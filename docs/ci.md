[`PastaPastaPasta/dashwallet-desktop`](https://github.com/PastaPastaPasta/dashwallet-desktop), which is
public, so the hosted Linux, macOS and Windows runners cost nothing. No workflow needs a secret, and every
job's `GITHUB_TOKEN` is read-only (`contents: read`) except release publishing and the jobs that open the

Every action a workflow uses directly is pinned to a commit SHA (the tag is in a comment). Actions those
actions call are not all pinned: `compnerd/gha-setup-swift` (pinned) is a composite action that refers to
`actions/cache/restore@v6`, `actions/cache/save@v6` and `actions/upload-artifact@v4` by tag. Its cache steps
are off by default, and the artifact upload runs only when its installer fails. Accepted, as for its
unverified installer below; pinning them would mean vendoring the action.

A new push to a branch, a pull request or `main` cancels that ref's running CI: a burst of merges runs only
the newest commit, which covers the merges before it. The scheduled and dispatched runs have their own groups
(the event is part of the group), so a merge never cancels them, and a re-run of an older run gets its own
group, so it never cancels the newest commit's run. `main-result.yml` counts a cancelled `main` run that had
already failed a job as red. `release.yml` still has one `main` group that never cancels a running run.
A merge that changes only docs (`docs/` and `*.md`, except the docs tests read and `Vendor/`) starts no CI
run. Every `run` step uses bash with `pipefail` (Git Bash on
Windows) unless it names another shell. Checkouts do not keep the job token (`persist-credentials: false`).

**Triggers.** A branch is checked once, through its pull request; branch pushes start no run. A pull
request runs at most the Linux checks: `lint`, `rust-linux`, `windows-cross-check` (the Windows code paths
cross-linted for MinGW on Linux: the workspace, then dw-app with `selftest`; not required yet), `desktop-renderer`
and `ui-playwright` in `ci.yml`, picked by its changed files (below), and `script-tests` and `decide` in `release.yml` only when it changes
`release.yml`, `ci/`, `packaging/` or `rust/crates/dw-app/tauri.conf.json`. These four `ci.yml` jobs and
`changes` are the required status checks on `main`. The hosted macOS runners (five at a time across the
account) were the bottleneck, so the macOS, Windows, deep-link, tauri-driver E2E and Linux Swift jobs, the
release bundles, and Playwright run on every push to `main` that is not docs-only (each merge; the release
bundles move to tags, the schedule and dispatches only in the pull request after #780), on a 02:47 UTC schedule
(both workflows; the scheduled release run builds and never publishes) and on a dispatch. The non-blocking
Windows Swift job runs only on the schedule and on a dispatch. To run everything for a branch before it
merges: `gh workflow run ci.yml --ref <branch>` and `gh workflow run release.yml --ref <branch>`.

**Pull request checks.** While the app is in development every pull request, funds code included, runs only
the fast checks and may merge in batches; Playwright, tauri-driver E2E, the Windows engine tests and the
rest of the platform matrix run on `main` and nightly. `ci.yml`'s `changes` job diffs the pull request's merge
commit against its base:

| Changed files | Runs |
|---|---|
| only `docs/` or `*.md`, except `docs/contracts/` (read by the Rust and vitest contract tests), `docs/design/E0-13-facade-coverage.md` (generated by `rust-linux`), code and config files under `docs/` (`.rs`, `.swift`, `.ts`, `.json`, `.toml`, `.yml`, `.sh`, `.py` and the like) and the renderer files the Rust tests read | `changes` only |

| anything else, unknown paths included | `changes`, `lint`, `rust-linux`, `windows-cross-check` (not required yet) and `desktop-renderer` |

`ui-playwright` runs on a pull request only when `FUNDS_FULL_SUITE` (the `changes` job's env in `ci.yml`) is
`"true"` and a funds path changed: any `.rs` or `.swift` file, `rust/`, `Sources/`, `Tests/`,
`Package.swift`/`.resolved`, any renderer file but i18n catalogs and stylesheets, or a path whose lower-cased
name contains a funds word (`send`, `sign`, `psbt`, `coin`, `fee`, `key`, `seed`, `phrase`, `wallet`, `lock`,
`pay`, `tx` and the others listed there). Such a pull request then runs all four required jobs. **Restore full
per-PR CI on funds paths before RC (11-30) / 1.0** by setting it to `"true"`.
When `rust-linux` doesn't run, `changes` runs `windows-paths.py`, as `lint` would. A push, a dispatch, the
schedule, or any failure of `changes` runs every job. GitHub counts a skipped required job as passed, and
cancelling a run while `changes` is pending skips the four jobs, so `changes` ("What this pull request
changes") is itself a required check: cancelled or failed, it blocks the merge.

**A red main is a stop.** The full matrix (Playwright, tauri-driver E2E, deep links, Linux Swift, macOS,
Windows and the release bundles) runs on pushes to `main`; a burst of merges is covered by one run (see the
concurrency note above). `main-result.yml` runs when a `ci.yml` or
`release.yml` run on `main` finishes: while the newest finished run of a workflow is red, one open issue
labelled `nightly-failure` ("Nightly failure: CI on main" or "Nightly failure: Release on main") names its
failed jobs and the pull requests merged since that workflow's last green run (the batch that broke it); the
next green run closes it. Main is fixed before anything else merges; the issue says so, and the required
pull request checks do not enforce it. A forward fix on top is fine; a revert is
not required. A cancelled run (a pending main run replaced by a newer one) reports
nothing.

The Linux Rust jobs install the WebKitGTK development packages first (the `rust` set of
`ci/github/linux-host-deps.sh`, the list in G-01's `apps/desktop/README.md`, through the cached `tauri` set below): once the Tauri crate `rust/crates/dw-app` lands,
`cargo build --workspace` needs them. `ci/linux/Dockerfile`, the Rust builder image, has them too. The
Swift images build only `dw-ffi` and do not.

The script downloads the packages under a deadline, up to three times, and installs them only once they
are all on disk. The runner image lists its regional Ubuntu mirror first, then `archive.ubuntu.com` and
`security.ubuntu.com`, and reads `noble-security` from `security.ubuntu.com`. apt leaves a stalled mirror too
slowly to finish under the deadline, and all three can be down together (2026-11-19). So when a download
attempt fails (except under Release's live-first, below, which leaves the mirrors alone), the script puts `azure.archive.ubuntu.com` first, drops the mirrors listed ahead of
`archive.ubuntu.com`, and points the `noble-security` source at the same mirror list, so it keeps
`archive.ubuntu.com` and `security.ubuntu.com` as fallbacks. When the mirror that failed is the Azure one
(some runners have it as their regional mirror, and on 2026-11-20 it was too slow for three attempts), it
goes last instead, so `archive.ubuntu.com` serves the next attempt; apt keeps what the failed attempt
downloaded. apt checks every package against Ubuntu's
signed indexes whichever mirror serves it. The download deadline is 6 minutes (`DW_APT_DOWNLOAD_DEADLINE`);
the two Rust jobs set 1 minute, since a download takes seconds and a stalled regional mirror otherwise
held them for the whole 6 minutes before the Azure mirror served the packages in about a second.
`ci/github/linux-host-deps-test.sh` covers this with stand-ins for apt and runs in the "Release scripts"
job.

**No live download where a cache can serve.** On 2026-11-23 a refused connection to the Tenderdash
archive failed Release's Linux bundle, and an apt outage failed Rust lint. Those two no longer depend on
the network once the cache holds them:

- `.github/actions/pinned-sources`, in every job that ran `install-protoc.sh`, after rust-cache, restores
  protoc and the Tenderdash sources from the Actions cache (key: OS, architecture, protoc version and a
  hash of both scripts), downloads them on a miss with retries, checks each against its pinned SHA-256
  on every use, and saves on a miss, except on a pull request: pull requests read main's entries and
  never write their own, so a new runner image or an edited script cannot make every open pull request
  save a copy and crowd rust-cache out of the repository's 10 GB. A mismatch stops the job before anything is built, with the cache
  key to delete when the cached copy is the bad one. tenderdash-proto's build script reads
  `$CARGO_TARGET_DIR/tenderdash-<commitish>.zip` when it exists instead of downloading, so the action puts
  the archive in `rust/target` and exports `CARGO_TARGET_DIR` as that same directory: every job that runs
  the action already builds there (the release bundles and `ci/github/release-stage.sh` read
  `rust/target`, as do the e2e scripts and `scripts/build-core.sh`; the fuzz job's own `--target-dir`
  wins for its output, and its build script still finds the archive). It runs after rust-cache because
  rust-cache hashes `CARGO*` variables into its key.
- `.github/actions/linux-host-deps` runs `linux-host-deps.sh tauri` with its `.deb` files in the Actions
  cache, keyed on the runner image (`ImageOS`, `ImageVersion`), the architecture and a hash of the two
  scripts. Every Linux job that needs WebKitGTK uses it: the tauri set includes the rust set, so Rust lint
  and Rust tests install the few GUI packages more (seconds) and share one entry of about 96 MB per image
  version with the Tauri jobs and Release's Linux job (measured 2026-11-23: rust set 92 MB, tauri set
  96 MB, compressed). A miss downloads as above and saves the `.deb` files with the Ubuntu
  `InRelease` files and `Packages` indexes that list them. A hit installs the cached `.deb` files directly, with no apt source
  configured, once
  `ci/github/apt-cache.sh verify` has checked the chain from the image: each `InRelease` against the
  image's `/usr/share/keyrings/ubuntu-archive-keyring.gpg` with gpgv (only its signed text is read), each
  `Packages` index against the SHA-256 its `InRelease` gives it, and each `.deb` against a `Packages`
  index; release files must also name this image's Ubuntu release and one of the pockets its
  `ubuntu.sources` lists (release, updates, security, backports; never `proposed`). Any break fails the
  job, with the cache key to delete. Pull requests read the entry and never save one, as above.
  Release's Linux job sets `live-first`: with an entry restored, it tries one live download first (60 s
  for the update, 180 s for the download) so that a WebKitGTK security update published since the entry
  was saved reaches the AppImage, and installs the verified cached set only when that download fails. That fallback writes `apt: cache fallback used` to the run summary, so a release built from the cache can be found by searching for that line. The `flatpak` and `swiftcrossui` sets are not cached, to spare the repository's
  cache budget for rust-cache.
- Still downloaded live: Rust toolchains (rustup), the Flatpak job's packages and Flathub runtime, the
  `swiftcrossui` set, Swift through swiftly or `compnerd/gha-setup-swift`, the Windows App Runtime
  installer, nightly's `dash_hash` and Docker base images, plus cargo's registry and git sources when
  rust-cache has none. On a miss, each cache above downloads as before.
- Residual for 1.0, pinned in #386 (1.0.x): the bundlers Tauri downloads itself, unchecked by us:
  linuxdeploy and its plugins for the AppImage, and NSIS for the Windows setup.
- Residual: if the checked Tenderdash archive fails to unzip, tenderdash-proto's build script deletes it
  and downloads it again (its second attempt) without our SHA-256 check. A checked archive that fails to
  unzip means a broken disk or runner, not a bad source.

use) with swiftly, and GTK 4 with `ci/github/linux-host-deps.sh swiftcrossui`. It builds the package's test

It runs on the runner rather than in a `swift:6.3.3-noble` job container, so it shares the free-disk step
and caching with the other Linux jobs.

`build-core.sh` reads the system libraries from rustc's `native-static-libs:` line. Under
`CARGO_TERM_COLOR=always`, which every workflow sets, that line ends in an ANSI reset. The script
dropped `-lc` from the module map, but `-lc<ESC>[0m` slipped through, so every object importing the core
asked the linker for a library named `c<ESC>[0m`. gold and lld both reported `cannot find -lc`, with the
escape invisible in the log. The script now strips colour codes before parsing.

**Caching.** `Swatinem/rust-cache` caches `~/.cargo` and the dependency part of `rust/target` per job,
keyed on `Cargo.lock` and the toolchain. rust-cache hashes `rustc -vV` of every installed toolchain into the
key, so every Linux job that restores the `ci-Linux` cache (Rust lint, Rust tests, Tauri E2E, the Linux
deep-links leg, Swift + UI T0 and `release.yml`'s Linux build) uninstalls every toolchain but
`rust/rust-toolchain.toml`'s (`ci/github/rust-toolchain-only.sh`): with the image's stable left in, a runner image that bumps it moves
every job to a key that nothing has saved yet. `actions/cache` caches SwiftPM's repository cache, keyed on
`Package.resolved`. A cold run builds the whole platform graph: it takes about 25–90 minutes per job,
depending on the job and the runner (about 45 for `Rust tests (Linux)`, which takes under 20 warm), and a warm one much less.
Only `ci.yml` on `main` saves the regular Rust caches (`ci-Linux`, `ci-mingw-Linux`, `ci-macOS`,
`ci-Windows`; a busy merge day can cancel every main run before macOS saves, and the 02:47 UTC run, in its own
group, saves then); `release.yml`'s build jobs and `nightly.yml` restore them and never save (nightly's fuzz job
keeps its own cache, since it also installs a nightly toolchain). Each restoring job installs its toolchains
as the saving job does, since the key hashes every installed toolchain: only `rust/rust-toolchain.toml`'s on
Linux, and that plus the image's stable on macOS and Windows. The manual
`gate.yml` and `tauri-selftest.yml` still save from whatever branch they run on. A cache is saved only when its job
succeeds. Past the repository's cache limit (10 GB by default), GitHub evicts the least recently
used caches, so a branch whose workflows still save their own caches can push `main`'s out.

**Disk.** The hosted runners have less free disk than agentbox, so the workflows set

## Funds review gate (`funds-gate.yml`)

A pull request that changes a funds path merges only with two records for its **exact head commit**: a
funds-reviewer verdict and an Opus code review, both approving. The funds paths are listed in one file,
`ci/funds-paths.txt`. All of dw-engine counts, except the files its `!` lines name as not funds (for example rates,
CSV export, avatars, banners and governance voting; the file has the full list), so a
new engine file is gated from the start. So do the keys, vault, PSBT, ProTx, CoinJoin and units crates, the
CLI wallet, the wallet files, app.sqlite's hold and barrier records, the bridges that carry these to the UI
(Tauri commands and capabilities, the Swift engine bridge), the renderer's amount and send logic and the
screen view-models that build money requests, the dependency pins, and the gate itself. Check a branch with
`git diff --no-renames --name-only origin/main... | ci/github/funds-gate.py match`.

A record is an HTML comment in a top-level pull request comment (the Conversation tab; a review body or an
inline review comment does not count) by the repository's owner, a member or a collaborator (bots never
count). An approve must sit on a line of its own, starting at the first column, outside a `>` quote or a code
block, so quoting a verdict never casts one. A block counts wherever it stands on a line of its own (indented
up to three spaces, even in code), because a stray block can only refuse. Post records with `funds-gate.py
record`: it puts the record on the comment's first line and refuses a note that contains one. A hand-written
approve in or after a list or an HTML block may not be read.

    <!-- dwd-review kind=funds verdict=approve sha=<40-hex head> model=claude-opus-5-5 -->
    <!-- dwd-review kind=review verdict=approve sha=<40-hex head> model=claude-opus-5-5 -->

Reviewer lanes post one with `ci/github/funds-gate.py record --repo PastaPastaPasta/dashwallet-desktop --pr <N>
--sha <head they reviewed> --kind funds|review --verdict approve|block --model <their model> [--note-file F]`.
It refuses when the head has moved since the review, and refuses any model but Opus (`claude-opus-…`); Sonnet
is never a reviewer. Rules:

- Only records naming the current head count. Any push, a merge of main included, makes the old ones stale.
- For each kind, the latest record at the head wins: `verdict=block` withdraws an earlier approve. "Latest" is
  by the comment's creation time; editing an old comment changes its record in place.
- A pull request that changes no funds path passes with no records.
- If the API truncates the file list, the gate treats the pull request as funds.

`funds-gate.yml` runs on `pull_request_target` (opened, pushed, reopened, ready for review, edited: a base
change alters the file list), on a pull request comment that adds, edits or deletes a record, and on a
dispatch (`gh workflow run funds-gate.yml -f pr=<N>`). For a pull request into `main` it posts the commit
status **Funds review gate** on the head: pending while it checks, then success or failure; an error after it
reads the pull request leaves it pending. If that first read fails, the previous status stays until the next
run, but the drain's check refuses on any error. A pull request into another branch gets no status, because a
status belongs to the commit and a stacked pull request at the same commit must not turn it green. If the head
or base moves while it reads the file list, it reads again, up to three times. It runs the gate from the pull
request's base branch (comment runs: the default branch), never from the pull request, and checks out no pull
request code. The status is advisory until `main`'s branch protection requires the context `Funds review gate`
(not the job name, whose run passes on a refusal). The PO's drain script runs the same `funds-gate.py check
--sha <head>` from origin/main before every merge and refuses on anything but a pass. That fresh check is the
authoritative one: a change to `ci/funds-paths.txt` on main does not re-run the status on open pull requests,
but the drain reads the new list. `lint` runs `ci/github/funds-gate-test.py`, which also checks that every
pattern in `ci/funds-paths.txt` still matches a tracked file.

## UI tests (U-07)

The renderer is tested in a browser against the **fixture backend** (`apps/desktop/src/fixture/`): Tauri's
mock IPC answers the generated commands (`src/api/generated/commands.ts`, typed by `CommandArgs` and
`CommandResults`) from a scenario's data and emits `engine://event` like dw-app's bridge. Nothing of the
engine is built or linked. Scenarios: `funded` (default), `empty`, `no-wallet`, `locked`, `large`, `xss`,
`dashpay-no-identity`, `dashpay-registering`, `dashpay-registered`, `lock-report-omitted`,
`lock-report-omitted-settles`, `lock-report-pending`, `lock-report-resolved`, `lock-report-call`, and `error-<class>` for each `ErrorData` class (see
`apps/desktop/README.md` for the URL parameters).

**No fixture marker or fixture literal in production.** The renderer imports the fixture only under the build-time constant
`__DW_FIXTURES__`, which is true for `vite` (dev server) and `vite build --mode fixture` and false for
`vite build`, so the production bundle has no fixture chunk. Vite's `noFixtureModules` plugin fails a
production build whose chunks hold any `src/fixture/` module, any module whose source carries the line
`// dw-fixture-module` (every fixture module starts with it, `fixture.test.ts` checks, so a copy or a
rename outside `src/fixture/` still fails), or the mock IPC, whatever imports it, and
`scripts/check-bundle.mjs` runs at the end of both builds. `dist/` fails if it contains the fixture's
sentinel string, Tauri's mock IPC or any **fixture sentinel**, derived on each build by
`scripts/fixture-sentinels.mjs` from the fixture modules, every file in `src/fixture/` of a type Vite loads
as a module (`.ts .tsx .mts .cts .js .jsx .mjs .cjs`), the `*.test.ts` vitest runs excluded, and from its
test data, the engine's vectors in `src/fixture/vectors/` (listed in `TEST_DATA`, of a type the script reads:
JSON). No module imports the vectors, but a copy loaded as `?raw`, `?url`, `?inline` or a JSON module would
ship them; a file in `src/fixture/` of any other type fails. A sentinel is a string literal (in test data, a
string value or key) of at least 8 printable characters that is not a plain word (one that is, once
surrounding spaces and punctuation are trimmed, needs 20) or an integer of 7 digits or more (the PRNG seed
`20261006`), less the literals the generated bindings (`src/api/generated/`, which
`codegen::tests::bindings_are_current` keeps exactly what dw-app writes) also hold in values, literal
types or field names, the error codes, transaction types and keys, computed rather than listed, and less `GENERIC`, literals a
production dependency holds too. `GENERIC` is empty: an entry needs a reason, a generic shape (a power of
two, a published PRNG constant, an alphabet; `sentinels.test.ts`) and a real collision, since `--production`
fails when `dist/` does not hold it. Every fixture module and test-data file must contribute a sentinel (or
be listed in `NO_SENTINEL` with a reason), and `fixture.test.ts` pins the exact list of files in
`src/fixture/`, so moving one out or adding one of another type fails there. Every file in the output is
scanned, chunks and emitted assets of any type, and so is every base64 `data:` URL in one, decoded; each
is also read with its `%XX` escapes decoded (an SVG is inlined percent-encoded) and its digit separators
dropped (a `?raw` copy of a module keeps `9_999_999`). `dist-fixture/`
fails unless it holds both markers and every sentinel of the modules (the positive control); the fixture
build does not bundle the test data, so its sentinels are expected only to be absent from `dist/`. The
negative controls, `scripts/guard-negative-control.sh` (in `ci.yml`), each import an unmarked copy in
`src/guard-copy/` from `main.tsx` and require `pnpm build` to fail at that file's sentinels: a copy of
`wallet.ts`, a new fixture module of type `.mts` and its copy, a copy of `errors.ts`, whose error codes are
exempt but whose messages are not, and a copy of `vectors/accept.json` loaded six ways: `?raw` (a string in
a chunk), `?url` (an asset of its own), `?inline` as `.txt` and `?url&inline` (base64 `data:` URLs),
`?inline` as `.svg` (percent-encoded) and as a JSON module (Vite fails `x.json?inline` itself).
What the check proves is that no fixture marker or sentinel is in `dist/`. It works per literal, not
per function: fixture code whose bundled part holds no sentinel (one function of an unmarked copy
imported by name, the rest tree-shaken away) would not be found, and neither would a copy deliberately
compressed or re-encoded as UTF-16, the same limit (BL-132). `pnpm tauri build` runs `pnpm build`, so
every app binary passes the check. dw-app has no fixture mode (`--fixture` is an unknown option).

## Main CI wall time

Measured over the 24 hours to 11-25 05:40Z (Actions API: 13 finished `ci.yml` main runs, 25 `release.yml`):

- Runners were not the bottleneck. A job waited for a runner 0.1 min at the median, 8.5 min at most
  (macOS included). The wait before a main run starts is the one-run-at-a-time concurrency group:
  16 min at the median, 49 min at most (7d52864dc, behind 6e9a194e9).
- A main CI run took 83–130 min (median ~104). Its last job was macOS in 10 of 12 runs, and Windows in the other 2.
- macOS `cargo test --workspace` took 45–90 min: the workspace compile took 5–55 min, and the
  dw-engine unit tests alone ~25 min. The Swift steps added another 10–30 min after it, one by one in the
  same job.
- The repository's Actions caches held 12.1 GB against GitHub's 10 GB cap, so saves evicted other
  caches. In 24 hours the CI Rust cache missed in 3 of 12 macOS runs, 3 of 13 Windows runs and 1 of 13
  Linux runs. A Windows miss costs 29–39 min of compile instead of 4–9. Release's own macOS cache took
  2.3 GB and saved its compile little (6–33 min on a hit, 11–43 min on a miss). Nightly's five Rust
  caches missed every night and were saved again.

So, trimming only (no new runners):

- `macos-swift` runs the Swift side beside `macos` instead of after it.
- A newer main push cancels the running main CI run; the newest commit's run covers the merges before it.
- A docs-only merge starts no CI run (the docs that tests read, and `Vendor/`, still do; on a very large push
  GitHub matches only part of the changed files). A merge never cancels the 02:47 UTC run or a dispatch: the event
  is part of the concurrency group.
- Release builds on tags, at 02:47 UTC and on a dispatch, not on every merge (in the pull request after #780,
  which rewrites `release.yml`).
- Release's macOS job and nightly (except fuzz) restore CI's Rust cache (`ci-<os>`) and never save one, which
  leaves CI's four (about 9.2 GB) as the only Rust caches the regular workflows save. Delete the old `v0-rust-release-macOS-*` entry once, after the
  merge (`gh cache delete <key>`), or it stays until it ages out.
- When runners are the wait, build and test on other compute (strix, agentbox, the Studio, boat.dev) and merge
  on that green build plus the required checks; fix a regression on main after.

### Fuzzing (H-02)

`rust/fuzz` (crate `dw-fuzz`, a workspace member) has ten libFuzzer targets for the outside data below, each
calling the entry points the app calls with it:

| Target | Input | Entry points |
|---|---|---|
| `link` | an opened, dropped, pasted or scanned link | `dw_uri::deeplink` (`classify_link`, `normalize_invitation`, `DashPayUserLink::parse`, `DashPayContactCode::parse`, `dpns_label`), `dw_uri::ext::parse_payment_uri` / `parse_payment_string`, `dw_uri::redact`; checks that a link the stash keeps is cut whole from a log line |
| `send_input` | text pasted on the Send screen or typed as an address | `dw_uri::core::handle_uri` (every network), `dw_uri::keyio` (`classify_address`, `decode_destination`, `decode_platform_destination`, `decode_secret`), amounts, `qr_matrix`; checks address and amount round trips |
| `qr_image` | an image scanned for QR codes | `dw_desktop::qr::decode` |
| `psbt` | a PSBT file or clipboard text | `dw_psbt::parse`, then `analyze`, `spent_output`, `input_signed`, `finalize`, `extract`, `fee_rate_per_kb`; checks the binary and base64 round trips |
| `dumpwallet` | a `dumpwallet` file | `dw_compat::dump::parse`, `write`, the label escaping, the mnemonic check |
| `listdescriptors` | `listdescriptors true` output, a descriptor | `dw_compat::descriptor::parse_listdescriptors`, `PkhDescriptor::parse` (checks that a written descriptor reads back when its checksum can be computed; a key outside the descriptor charset, such as `pkh(é/0/*)`, still goes to the parser) |
| `walletdat` | an SQLite wallet.dat's records (SQLite itself is fuzzed upstream) | `dw_compat::walletdat::SqliteWallet::from_records` (what `read_sqlite` streams its rows into), `hd_root` without a passphrase and, for an encrypted wallet, with the passphrase the input carries |
| `walletdat_bdb` | a legacy Berkeley DB wallet.dat file, with a passphrase | `dw_compat::walletdat::read_bdb_bytes` (`dw_compat::bdb`'s page, internal-node and overflow reader, then the record parser), `hd_root` as for `walletdat` |
| `avatar` | avatar bytes from a profile's URL with its zoom crop; a picked picture with its crop | dw-engine's avatar decoder (`ingest`, `ingest_file`, through the `fuzzing` feature's `platform::fuzzing`) |
| `invitation` | an invitation link | the claim's parser (DP5-01's normalization, then platform-wallet's `parse_invitation_uri`) |

The wallet targets try the passphrase only when the wallet's `mkey` records ask for 50 000 key derivation rounds or
fewer in total (`FUZZ_ROUNDS`); the import itself allows up to 10 000 000. Above the cutoff a passphrase attempt
takes long enough that libFuzzer would report a slow input, so those inputs stop after the unencrypted checks.

Seeds (`rust/fuzz/src/seeds.rs`) are the existing test vectors (`testdata/`, dw-uri's link corpus), plus inputs
built from fixture keys: avatar pictures with generated pixels; a version 3 special-transaction PSBT; the records
of `desc_plain.dat` encrypted as Core encrypts them, but under a 25-round `mkey` so the passphrase attempt decrypts
them; `bdb_tree_overflow.dat` (the plain HD wallet as an internal root over two leaves, with one value in an
overflow chain); and claimable regtest invitation links the library encodes (with `--features engine`). `rust/fuzz/regressions/psbt/` holds one fuzz
mutation, the input that found the special-payload bug; it is replayed as a rejection, and the accepted version 3
PSBT seed replays the fix.

`cargo test --workspace` replays every seed of the eight targets that build without the `engine` feature, and
every input saved under `rust/fuzz/regressions/<target>/` (a minimised finding kept after its fix), through the
same harness on stable, in about 3 seconds of a debug build on a desktop-class x86-64 workstation (about 2 s of CPU time); `cargo test -p dw-fuzz --features engine` adds `avatar` and `invitation`.

No target covers yet: image-to-route dispatch, the InstantLock decoding of an invitation at claim time, peer
frames and governance messages, Platform profile and contact documents, native backup headers and bodies, vault
files, and `settings.json`. The roadmap's H-02 criterion of 24 hours without a crash has not been met yet: the
targets have run for 60 seconds each, and nightly runs 10 minutes each.

Run it locally with cargo-fuzz 0.13.2 and the pinned nightly (`rustup toolchain install nightly-2026-10-09`,
`cargo install cargo-fuzz --version 0.13.2 --locked`):

```sh
scripts/fuzz.sh ~/dw-fuzz 1200         # every target, 20 minutes each
scripts/fuzz.sh ~/dw-fuzz 600 psbt link # some targets
```

The build is release with debug assertions, overflow checks and AddressSanitizer. A target that finds a crash,
an input slower than 30 s (`DW_FUZZ_TIMEOUT`) or more than 4 GB of memory (`DW_FUZZ_RSS_MB`) leaves the input in
`<work dir>/artifacts/<target>/` and fails the script. To fix one, from `rust/`: reproduce it with
`cargo +nightly-2026-10-09 fuzz run --fuzz-dir fuzz --target-dir target/fuzz --features libfuzzer,engine <target> <input>`,
minimise it with `cargo … fuzz tmin … <target> <input>`, fix the parser, and commit the minimised input under
`rust/fuzz/regressions/<target>/` so the replay test fails without the fix.

## `release.yml` (PK-01, PK-02; 0.1)

On a push to `main`, the 02:47 UTC schedule, a dispatch and a tag `v*` (pull requests that change the release scripts, `release.yml`, `packaging/` or the app version run only `script-tests` and `decide`; see Triggers below). One job per OS builds the release-profile app without the
`selftest` feature (each job restores CI's `ci-<os>` Rust cache and saves nothing; Node 24, pnpm; the Windows `unistd` shim as in
`ci.yml`):

| Job | Runner | Output (staged by `ci/github/release-stage.sh` as `dash-wallet-<version>-<suffix>`) | Measured (cold cache, rel6) |
|---|---|---|---|
| macOS | `macos-latest` | `pnpm tauri build --target universal-apple-darwin --bundles dmg`: `macos-universal.dmg`, ad-hoc signed (`signingIdentity "-"` in `tauri.conf.json`), not notarized | 45 min (build 42) |

Each job then launches the built app for 30 s on an empty `--datadir` with `--network regtest --no-platform
--dapi https://127.0.0.1:1 --window-size 960x640` (nothing syncs, nothing leaves the runner), fails if the
process dies, and uploads `launch-<os>`. Linux runs the AppImage under Xvfb (`linux-release-launch.sh`); the Flatpak job runs

runners the screen capture is black or shows the runner console although the window exists (a real Windows 11
VM renders the same build), so there the check is "the process is alive after 30 s", with the window title
logged; real screenshots of those two come from a person at release time.

Flatpak limits (PK-01):

- The sandbox has no access to the system secret store (no `--talk-name=org.freedesktop.secrets`), so a wallet in
  the Flatpak needs a passphrase. The secret-store option fails closed, and onboarding asks for a passphrase.
- `checksums` waits on the Flatpak job, so a Flathub outage or a slow runtime pull holds up every main and tag
  publish. `flatpak-bundle.sh` retries once.
- `packaging/flatpak` is a self-hosted manifest and is not on Flathub. Submitting it needs a `url` + `sha256`
  source (the tagged `.deb`), `<screenshots>` in the metainfo and a `vcs-browser` URL.

The `sbom` job (`ubuntu-24.04`, same conditions as the build jobs) writes two CycloneDX JSON SBOMs with
`ci/github/release-sbom.sh` and uploads them as `dist-sbom`: `sbom-rust.cdx.json`, the `dw-app` crate's
dependencies for every target (`cargo-cyclonedx` 0.5.9), and `sbom-npm.cdx.json`, the renderer's declared
production npm dependencies from `pnpm-lock.yaml` (`pnpm sbom`; build tools such as Vite are not listed). Both carry
the commit's time, no serial number and no machine path. The `checksums` job downloads the five `dist-*` artifacts
(`dist-macos`, `dist-windows`, `dist-linux`, `dist-flatpak`, `dist-sbom`), checks there are seven files (five bundles, two SBOMs),
writes `SHA256SUMS` in `sha256sum` format (file names only), checks it with `sha256sum -c` and uploads everything
as `release-v<version>`.
`ci/github/release-version.sh` names the files: the tag's version for a tag (a plain `vX.Y.Z` must equal
`tauri.conf.json`), else `<version>-dev.<run>.g<short sha>`.

**Triggers and publishing (DEC-1058).** The workflow runs on pushes to `main`, on tags `v*`, on pull requests that touch the release paths,
on its schedule and on `workflow_dispatch`; all but pull requests build and upload CI artifacts with `contents: read`. Only the `publish` job
has write permissions (`contents`, `id-token`, `attestations`), and its `if` admits a push to `main` or to a release
tag only when the read-only `decide` job (`ci/github/release-decide.sh`) says `publish=true`: the trigger is a push
to `main` or a tag `vX.Y.Z[-rc.N]`, in `PastaPastaPasta/dashwallet-desktop`, **and the commit is an ancestor of a
freshly fetched `origin/main`**. A fork's pull request, a branch, a dispatch, a dry-run tag and a release tag on a
commit outside `main` therefore never start the job that holds the write token. This check is code of the pushed
commit, like the workflow, so it cannot stop a tag whose own workflow file was edited; that needs an environment
deployment policy or a tag ruleset in the repository settings. `release-publish.sh` repeats the ancestry check
(second line). `decide` also gates the build: a branch push or pull request that changes only `docs/`, `*.md`, the
Swift trees (`Sources`, `Tests`, `Apps`, `Vendor`, `Package.*`) or the unrelated workflows skips the build
jobs and so `checksums` (`script-tests` still runs); main, tags and dispatches always build. A new push to a branch
or pull request cancels that ref's running release build. Main and tags are never cancelled; main builds one
commit at a time, and a newer pending main run replaces an older pending one. The `publish` job checks
out the full history, runs `ci/github/release-publish.sh` and publishes:

- push to `main`: an immutable prerelease `v<version>-dev.<run>+<short sha>` (never edited; skipped if it exists)
  and the rolling prerelease `continuous` with stable names `DashWallet-continuous-<os-arch>.<ext>` and its own
  `SHA256SUMS`. `continuous` is replaced as one generation, with a transaction record (the asset `txn.json`: old and
  new commit, old and new notes, the hash of the new `SHA256SUMS`): recover from an interrupted earlier run (in every
  run, an older one too, which then leaves `continuous` alone), upload the record and every new file as `<name>.new`,
  then per name rename the old asset `<name>.old` and the new one `<name>` (`SHA256SUMS` last), move the tag, rewrite
  the notes, and only then delete the `.old` assets and the record. Any failure after the first rename, and a cancel
  (SIGINT/SIGTERM), rolls back: every name is restored from its `.old` (a name the old generation lacked is
  deleted), the tag and the notes go back (also when the failing API call had in fact taken effect).
  The API is not atomic, so for tens of seconds during the renames a file
  can be missing for the two calls between its renames, or newer than the `SHA256SUMS` next to it (downloaders retry;
  see `verifying.md`). A hard kill or an API outage can leave canonical names missing, `.new`/`.old` leftovers,
  mismatched checksums, or a tag and notes that describe the other generation, until the next publish, whose first
  step repairs all of it: leftover `.new` deleted; a missing name restored from its `.old`; if the binaries do not match
  `SHA256SUMS` the whole old generation is restored, else the `.old` copies are dropped; then the record says which
  generation the assets are, and the tag and notes are set to match it. By hand: rename each `<name>.old` over the
  missing or new `<name>`, delete stray `<name>.new` and `txn.json`, set the tag and notes to the commit of the assets,
  or re-run the publish job. The tag moves after the assets and never backwards (an older run finishing late leaves
  `continuous` alone, after repairing).
- push of a tag `vX.Y.Z[-rc.N]` (on `main`): a full release for `vX.Y.Z` (GitHub marks the highest version
  Latest), a prerelease for `-rc.N`, with the run's files (notes from
  `docs/release/X.Y.Z-notes.md`), nothing rolling. `v0.0.0-rel<N>` dry-run tags only build.
- `actions/attest-build-provenance` runs before the release is written, on every file (the five bundles and both
  `SHA256SUMS`); the stable-named copies have the same bytes, so one attestation covers both.

The publish concurrency group is per ref (`release-publish-main`, and one per tag), never cancelling. GitHub
keeps one pending job per group and cancels the older pending one when another arrives. Main's builds run one at
a time and a newer pending build replaces an older one, so a burst of pushes skips the immutable release of a
middle commit; `continuous` follows the newest build that published (it never moves backwards, and its notes
name its commit). A tag's
release cannot be displaced by a main push. Repository setting: "Immutable releases" must stay **off**, since
`continuous` renames and deletes assets and moves its tag (the per-build releases are immutable by this workflow's
own rule, not the setting). An interrupted `gh release create` can leave a draft or an incomplete release; the
script then fails with a message rather than treating it as done, and the leftover is deleted by hand. The `decide` job
(read-only) runs `release-publish.sh classify`; `publish` needs its verdict as well as a push to `main` or a `v*`
tag. Dev tags (`v*-dev.*`) do not trigger the workflow. `gh` reads that fail with anything other than a 404 are never read as "absent". The publish script does all the
reads that decide what to write (the immutable release, the `continuous` tag, release and asset list) before its first
write, so a failure there stops it with nothing written; the reads of a recovery or rollback come later, and a failure
there stops that step (the immutable release may already exist by then).

The `script-tests` job runs `ci/github/release-publish-test.sh` (a fake `gh` and a
scratch git repository: which triggers publish and which refuse, the decide verdicts including an off-main tag, and
the `continuous` swap under a failed write, an outage and a kill at every write) on every run. For a dry run against
the real repository: `DRY_RUN=1 ci/github/release-publish.sh publish` after `prepare` runs the reads and prints
each write. Nothing is signed by hand and no PGP key is involved before 1.0; see `docs/release/verifying.md`.

## `tauri-selftest.yml` (G-02)

```sh
gh workflow run tauri-selftest.yml --ref <branch with G-01> -f os=both            # or macos / windows
gh workflow run tauri-selftest.yml --ref <branch> -f os=windows -f theme=dark \
    -f selftest_args="--datadir D:/a/wallet --network regtest \
      --selftest-passphrase-file D:/a/pass"                                    # instead of the new wallet
```

Per OS (`macos-latest`, `windows-latest`): Node 24 and pnpm from `apps/desktop/package.json`,
`pnpm install --frozen-lockfile`, `pnpm tauri build --no-bundle --features selftest` (the renderer and a
dedicated self-test binary `rust/target/release/dash-wallet`: release profile with dw-app's `selftest`
feature, which every release and packaged build leaves off, so they have no self-test options,
commands or grants; E0-13 D17). Without `selftest_args` the job builds `dwcli`, which makes an
encrypted vault and a wallet in a fresh regtest data root (`--no-platform`). `ci/github/regtest-fund.py`
then starts a regtest `dashd` from the verified Dash Core release (`regtest/scripts/fetch-dashcore.sh`:
the tarball on macOS and Linux, the zip on Windows), pays the wallet 1.5 DASH, mines the payment into a
block and runs `dwcli sync` until the wallet holds it, then stops `dashd`. The history stays in the data
root, so the app, which opens it on the real engine without a peer, shows the transaction. The vault's
passphrase file goes to the self-test only (`--selftest-passphrase-file`); the job creates it under
`umask 077` and `chmod 600` (Windows: `icacls`, inheritance removed, full control for the job's user only),
because `selftest_unlock` refuses a file others can read (E0-13 D16). (Until U-07 the default was
`--fixture`, an in-app TypeScript wallet; the fixture backend now runs in browsers only.) Then:

1. `dash-wallet <app args> --selftest-passphrase-file <file> --selftest selftest-<os>.json` within 10
   minutes. dw-app unlocks the vault with the file's first line (`selftest_unlock`, refused without
   `--selftest`; the renderer never holds the passphrase). The app renders Overview, Transactions and the
   detail sheet of the newest transaction, then locks to render the lock screen and unlocks again, in light
   and dark, and writes the `data-testid` boxes, style checks, IPC timings and security probes. The app
   exits 0 whatever it found, so `ci/github/selftest-judge.jq` judges the report. The step fails when the
   app fails, times out or writes no report, or when the judge finds any of these: a checkpoint report
   (`final: false`) rather than the final one; any of the eight screens (`light`/`dark` × `overview`,
   `transactions`, `txDetail`, `unlock`) not recorded; no history row shown; a failed style check; no
   `security.navigation` probe; or a security probe that says `NOT REFUSED`. No failed check is excused
   (until U-07 r1 the history checks were, because the wallet had none): on the funded wallet every check
   finds its element or is not applicable (on Linux, 212 checks, 0 failed, 12 not applicable).
   `ci/github/selftest-judge-test.sh` (run by `ci.yml`) proves that a
   report missing each required screen fails. With `selftest_args`, pass `--selftest-passphrase-file`
   (a file only its owner can read) and a wallet with history yourself, or the judge fails the run. The populated fixture screens are
   also checked by Playwright in `ci.yml`, in Chromium and WebKit. The screens, counts, paint times and
   probes go to the run's step summary.
2. `dash-wallet <app args> --theme <theme>` launched again, with a screenshot (the helpers above). The window
   is 1280×820, and the Windows helper captures the primary screen, which may be smaller.

On Windows a step first logs the WebView2 runtime version, or warns that none is registered.

Both, with the logs, are uploaded as `tauri-<os>`. Installers (MSI/NSIS, dmg) are not built here: that is
U7 in G-02's `ci/gate/tauri.sh`, or PK-02 / W-01 later. On a ref without `apps/desktop` the job fails at its
first step and says so.

   `LayoutSystem.computeStackLayout` → … → `AppKitBackend.size(text:)`; run
