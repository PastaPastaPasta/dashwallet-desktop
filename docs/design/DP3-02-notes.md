# DP3-02 + DP3-03 notes

Decisions taken where DASHPAY §2.3, the ROADMAP rows and the m4 contract are silent. The contract carries the
outcome (m4 item 47, m1 `history_page` / `tx_detail` / receive rows); this file says why.

## DP3-02: counterparty, contact activity, frequent contacts

| # | Decision | Why |
|---|---|---|
| D1 | A history record is a contact's when the output it describes pays an address of one of the identity's DashPay accounts with that contact: a receival account for a receive record (*from*), an external account for a send record the wallet funded (*to*). Addresses come from every pool address the wallet holds, not only used ones. | DIP-15 gives each (user, friend) pair its own account, so the address names the pair without Platform. The pools a wallet holds always cover what it detected, so a received payment whose coin was later spent is still attributed after a restore; the library's `reconcile_incoming_payments` sees only unspent coins and would lose it. |
| D2 | A send to an external address past the resident pool takes the library's word: its `Sent` (not `Failed`) payment entries for the txid, when they name exactly one (identity, contact) pair, the transaction has exactly one unattributed payee record, and no output pays any DashPay address the wallet holds. Anything else stays unattributed. | A restore regrows external pools only to the gap, but the library's DashPay pass rebuilds `Sent` entries from the transaction history. The library matches an entry by any output: when one pays a known DashPay address (e.g. the wallet's own other identity, which dash-qt shows as change), the entry names that output, not the payee (Opus r1). Guessing would show a wrong name, which is worse than none. |
| D3 | Not attributed: a payment between two identities of one wallet (dash-qt calls it SendToSelf, one record with no output), mixed or foreign-funded debits (`Other`), coinbase, CoinJoin mixing, denominations and collateral, Platform transfers. A CoinJoin Send (mixed coins paying a contact) is attributed. | These have no single payee record, or no contact on the other side. |
| D4 | `Counterparty` on a record has no provenance flag. `username` comes from the contacts' username cache (DP2-01); a history read asks for names it lacks in the background, and a landing name sends `Platform{Contacts}`. `display_name` / `avatar_url` from the cached profile. | It is display data (m4 §5); DP3-04's money-move gate checks trust itself. The m1 sync-read rule forbids a fetch inside the read. |
| D5 | Hosts re-query history on `Platform{Contacts}` and `Platform{Payments}` as well as `HistoryChanged`. | A username lands after the first read; a restored send is attributed after the library's pass. No new event. |
| D6 | `TxDetail` gains no field of its own: its `records` carry `counterparty`. | One place, the same as the history row. |
| D7 | The history text filter does not match contact names or usernames. | dash-qt's filter is address / label / txid (m1). Searching names needs the names at filter time, which a sync cache cannot promise. The UI rows (DP3-06/07) can ask again. |
| D8 | `contact_activity`: 50 items per page; one item per (transaction, direction); `amount` sums the outputs to or from the contact (no fee, no change); `timestamp` the block time, else first-seen; `height` the block height. Abandoned, not-accepted and conflicted transactions are left out. | The design gives neither page size nor amount rule. The block time follows DEC-114 (authoritative only); first-seen covers unmined ones. A payment that never moved money is not activity. |
| D9 | Activity order: mined by block time newest first, unmined first, then txid. The cursor is 64 characters: a 15-hex-digit tag of the query (the first 60 bits of SHA-256 over the owner's and the contact's 32 bytes and a filter byte), 9 hex digits of the time (a block time is a `u32`; unmined: 2^32, after every block time), the txid's first 39 hex digits, `s` or `r`. A cursor the call did not issue, including one another query issued (another identity, contact or filter), is `invalid_argument` (Sol r1), except with probability about 2^-60 for another query's cursor (the tag can collide, Sol r2). An accepted one only positions the current query's own results at its key, so it exposes nothing of the other query; the tag is a misuse check, not a guarantee. Pages never repeat or skip for an unchanged set, unless two same-time, same-direction txids share their first 156 bits (infeasible in chain data; the two would be one item); a payment mined between pages, an out-of-order block time or a reorg can move one across the cursor. | A keyset cursor (like m1 history's): new payments never shift later pages; hosts re-query from page 1 on `HistoryChanged`. 39 hex digits (156 bits) keep the cursor within m4's 64-character id form and are unique in practice; 9 time digits instead of 16 widen the tag from 32 to 60 bits in the same budget (Sol r2's 32-bit collision pair is a test); the direction disambiguates a transaction with both. Without the tag an `All` cursor would page a `Received` query from a point it never showed, silently skipping or repeating. |
| D10 | `contact == identity` is `contact.self`; an identity not this wallet's is `identity.not_found`; a contact never paid is an empty page. | The same refusals as DP2-02's calls. A stranger is no error: there is simply nothing. |
| D11 | Frequent strip: Android's rule. Established, not hidden contacts; payments in the last 90 days; the most-paid first (count, then the latest payment, then the id), then the most-paying to fill the limit; never a contact with no payment; `limit` clamped to 1–20; an unmined payment counts as now. | Android's `getTopContacts` ranks sent then received over 90 days; iOS has no strip. Ties need an order that does not flicker. |
| D12 | The strip is sync: it reads the contacts read model and the history in memory. While a writer holds the library's state it answers from the last view (pools, payees) it read, and is empty before one. Each call rebuilds the view and walks the window's history (O(wallet), memory only). | The m1 sync rule. The busy window is short (a sync flush); an empty strip for one read is harmless. Caching the view across calls is a later optimisation if a large wallet shows it. |
| D13 | The OS notification for a payment stays M2's `NewTransactions`, with no contact name. | Out of scope for an engine-only task; the m4 residual says so. |
| D14 | `dw-app`'s `TxRow` binds `counterparty` as optional (left out when `None`); `dw-ffi` withholds it until E0-13. | Hosts get it now without changing the TS fixtures; the Swift bindings are frozen until E0-13. |
| D15 | `reserve_contact_payment_address` (E0-11's carried branch) is not needed. | Attribution reads the pools the wallet already holds; nothing here issues an address. The platform pin is unchanged. |
| D22 | A script DashPay accounts of two sides (owner, contact, direction) hold is nobody's: two contacts' external accounts, two receival accounts, or a receival and an external one. So is every address of two sides' accounts whose first addresses match (one xpub), including addresses past where the other's pool reaches. Their outputs stay unattributed in history, activity and the strip, and the library's word (D2) is refused for any transaction with an output to them. Accounts of one side that share a script keep it. This also covers a contact that gives one xpub to two of our identities (all its payments unattributed), and two identities of one wallet paying each other (each's external account is the other's receival one; harmless, as those are SendToSelf, D3). | A contact chooses the xpub of the external account we pay it through, so it can derive another contact's addresses (a payment to Bob shown as one to Mallory) or our receival addresses for another contact. Treat collisions as adversarial (Sol r1); a wrong name is worse than none. Pools grow from index 0 independently, so after a restore one account's pool can reach further than the other's; the first address decides the xpub without the xpub itself, which the managed account does not keep (Opus r2). |
| D23 | Amends D22: an external account whose xpub another side's account shares (by D22's first-address test) names a pair whose library `Sent` entries (D2) are refused, for any output, not only resident ones. An address of the shared xpub beyond both pools matches no resident script, so D2 alone would take the library's word and name either contact. Only the external accounts' pairs are kept: D2 attributes only sends. A pair whose own external account is not shared keeps D2. | D22 requires every address of a shared xpub to stay unattributed, and after a restore the payments past both pools are exactly D2's case (Sol r2). The pair, not the address, is what the library's entry names. |

## On U-03's screens (follow-merge of main 6b989904)

| # | Decision | Why |
|---|---|---|
| D24 | A row's title (U-03 D14's `txTitle`) is the label, else the contact's name, else the type title; the table's Address / Label column (`rowParty`) is the label, else the name, else the address. The name is the display name, else `@username`; with neither (the username lands later) the row keeps its type title and address, never the identity id. The detail sheet adds a "Sent to contact" / "Received from contact" row above the address. | A label is the user's own word and dash-qt shows it first; a contact name is better than "Sent" but an id is not a name. The address stays: attribution is display data (D4), not a replacement for what was paid. |
| D25 | The bridge refreshes history and the detail sheet on `Platform{Contacts}` / `Platform{Payments}` (D5), and the receive reads (QR username, requests) on `Platform{Identities}` / `Platform{Names}`. Receive's QR asks `receive_username` and passes it to `build_payment_uri`; a request's sheet shows its `@username`. | U-03's bridge sent every `platform` event to the DashPay keys only, so a username landing after the first read would not reach Activity, nor a new main name the QR. |
| D26 | Follow-ups, not wired here: the row's leading avatar (`RowDecor.leading`; it fetches a contact-chosen URL, so it waits for the DashPay avatar policy), a tap through to the contact, the Home frequent-contacts strip and the contact activity list (DP3-06/07, which also own D21's Settings toggle). | Each needs UI that U-03 has no place for yet; the engine calls exist and are tested. |

## DP3-03: the username in Receive and in payment requests

| # | Decision | Why |
|---|---|---|
| D16 | The username is the main name of the wallet's main identity (`IdentitySummary.is_main`, `main_name`). | iOS uses the wallet's DashPay username; the desktop's "main" choice (DP1-05) is that identity. |
| D17 | The URI is dash-qt's `formatBitcoinURI` followed by `user=<username>` last, as iOS's `PaymentURIBuilder` (from DashSync's `DSPaymentRequest`) writes it. The name is percent-encoded; a DPNS label is unreserved ASCII, so the bytes match iOS's raw append for every real name. dash-qt's parser ignores the key. | Byte parity with iOS for real names; encoding guards anything else. |
| D18 | `ReceiveRequest.username` is computed when the request is read, not stored with it; a stored request's `uri` follows the current main name. | A request outlives a name change; showing a name the wallet no longer has would point payers at the wrong user. No schema change. |
| D19 | `None` (a plain Core URI) without a main identity or name, while a sync pass holds the identity state (`names_updating`), or when Platform's state cannot be read; never an error. | The username decorates a Core request; a receive screen must not fail on Platform. |
| D20 | A new async m1 call `NetworkSession::receive_username(id)` serves the plain Receive QR; `dw-app`'s `build_payment_uri` gains `user`. `dw-ffi` keeps its signatures (frozen until E0-13). | The Receive screen builds its own URI (QT-085); the read touches the name rows (DEC-124), so it is async and runs off the runtime threads. |
| D21 | Every receive request and Receive QR carries `user=` when the wallet has a main name. **Ruling (manager):** keep it by default; the opt-out is a Settings privacy toggle, "Include my username in payment requests", default on. **Follow-up (DP3-06/07):** the UI toggle and its setting; the engine calls then take the flag (`receive_username` returns `None`, and `create_receive_request` / `receive_requests` leave `username` out and build the plain URI, when it is off). Not threaded this round: the stored-request reads build `uri` in m1 calls that dw-app and dw-ffi share (dw-ffi frozen until E0-13), so the flag is not a one-line change. | iOS parity (IOS-055). It links the Core address to the DashPay identity for whoever sees the QR, so the user can turn it off. |
