## Flow of a link

1. The OS hands the link over.
   - Linux and Windows: a launch argument. When the app already runs, the second launch's
     single-instance plugin forwards its whole command line to the first and exits. Where it
     cannot (no session bus, another Windows session), the second launch stops at the data root's
     instance lock and the link is not delivered (D2).
   - macOS: `RunEvent::Opened` (LaunchServices keeps one instance).
2. The shell keeps the arguments in one of the four schemes. It queues each one (`Inbox`: at most
   16 links, each at most 4096 bytes, zeroed on drop), brings the window forward and sends
   `shell://event {kind: "linksPending"}`.
3. The renderer listens for `linksPending`, then calls `takeLinks(network)` once at start-up and
   after each event, one call at a time (D23). dw-app
   routes each link for the window's network into a `LinkRoute`.
4. The renderer opens the route, or shows a toast saying why it did not.

## D-rows

| # | Decision | Why |
|---|---|---|
| D1 | The toolbar chip is the DashPay identity chip: "Join DashPay", "Registering…" or "@name · Pending", and an avatar with @name, which opens My Profile. Network and sync stay in the title and the status bar. | DASHPAY §4. UX-SPEC §4.1 keeps network badges out of the toolbar. |
| D2 | One process per data root. `run` resolves the root first: `--datadir`, else the platform app-data directory (`<data_dir>/org.dash.wallet.desktop`, as Tauri finds it). It creates the root (0700 on Unix; on Windows it inherits the profile's ACL) and canonicalizes it, and from then on everything takes that one path: the instance name, the lock, the window state and the engine. A second launch hands its command line over through `tauri-plugin-single-instance` on Linux and Windows. On Linux the D-Bus name is the bundle id plus a hash of the canonical root, for the default root too. Windows keys the instance by bundle id, one per user session (forwarded links: D22). The backstop on every OS is an exclusive advisory lock (`flock` / `LockFileEx`) on `<root>/instance.lock`. `run` takes it before any window, webview or tray icon exists; the engine opens later, in the setup hook. With the plugin it is taken right after the build, when a launch that can forward has already done so and exited. Without the plugin it is taken before the build, so a refused launch ends before GTK starts (and GLib autolaunches a session bus). It waits up to 3 s for a holder, so a launch during the previous instance's shutdown gets in. The file is opened as a sole regular file, never through a symlink. A process that can neither take it nor hand over exits with "another Dash Wallet is already running on <root>" (`app.already_running`) and never opens the wallet. On Linux the shell probes the session bus first; with none, it skips the plugin, logs that, and relies on the lock. macOS has no plugin: LaunchServices keeps one instance and hands links over as `RunEvent::Opened`, and a direct launch of the binary stops at the lock. Upgrading from a build before r1: the Linux default root's bus name changes, and an older build takes no lock, so an old and a new build could each open the wallet once. There is no release before U-01. | dash-qt keys its IPC server by data directory, and two wallets and parallel tests run side by side. Sol r1 M1: the name must not depend on how the root is spelled, or on whether it exists yet. Sol r1 M3: the plugin panics on a malformed bus address and does nothing without a bus, and the engine's `app.sqlite.lock` is shared, so it does not exclude a second process. The plugin's macOS socket has a fixed name in the shared `/tmp`, which another local user could claim first and so swallow every launch and its arguments. |

Run-time registration writes into the user's `~/.local` and registry. The packages already register the schemes. |
