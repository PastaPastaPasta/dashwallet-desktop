# MG-00: Masternodes sidebar item — UX spec, mocks and decisions

ROADMAP MG-00 (release 1.1, DEC-01, DASHPAY §5a). The spec itself is **UX-SPEC §4.25**; it replaces §4.22–4.24,
which now point to it. This file holds the mock index, the decisions (D-rows) the spec cites, the
follow-ups for MG-01…MG-13, and the questions left for pasta. Design only: no renderer code changes.

The look follows the DashPay screens (U-02…U-05, DP2-07), and the flows follow mobile where mobile has them:
iOS `MasternodesScreen` for my and tracked masternodes, keys, credit withdrawal and the voting privacy note.
Neither mobile app has governance proposals, registration or shared masternodes, so those screens are new. They
are built from the same parts: split view, cards, sheets, wizards and inline passphrase. Facts come from the
parked branches (`m3/r2-governance`, `m3/r3-protx`) and from Dash Core v24.0.0-rc.3 (`0364ed626e`). They are
the protocol limits, fee, vote rules, PoSe and shared-masternode rules the copy relies on.

as they are, or map them to components.

## §5a in/out review

Every screen was checked against DASHPAY §5a. The left column (owner side) maps to screens as follows:

| §5a (in) | Screen |
|---|---|
| Governance list and detail, voting one or many masternodes, creating a proposal (fee, confirmations, submit, resume), clock, superblock dates, budget | §4.25.3, §4.25.4 |
| My masternodes (collateral, owner, voting or payout key in the wallet), tracking and attaching keys, SPV status, payouts in history, evonode status and credits, credit withdrawal to the payout address | §4.25.2 |
| Registration wizard: regular and evonode; FundNew, ExistingUtxo, External with a signed message; operator public key, service address and Platform details as given; self-operator fills the operator key from the keychain | §4.25.5 |
| ProUpRegTx (voting, payout or operator key) | §4.25.6 |
| v24 shared masternodes: creation, reward-address change, key rotation, dissolution, standby | §4.25.8 |
| Optional contested-name voting (MG-07) | not specified here; MG-11 reuses §4.25.4's rows (follow-ups) |

The right column (out) appears only as explanation:
- ProUpServTx (service update and Unban) and ProUpRevTx (revoke) are one explanation sheet. There are no forms and no disabled lookalike buttons (D24).
- No operator BLS secret is generated or held outside the keychain reveal (D27).
- Platform node operation and node administration don't appear at all.

One flow sits on the line and stays in: **Release collateral** (D38). It sends nothing. It unlocks the
collateral coin locally, and spending that coin is an ordinary payment that ends the masternode by Core's rules.

|---|---|---|
| D1 | Show the **Masternodes** sidebar item when any of these holds: the wallet has a masternode role (collateral, owner key, voting key, payout script, share refund: Core's `protx list wallet` set, from `Masternodes`); it holds an unspent output of exactly 1,000 or 4,000 Dash; it tracks a masternode or has a registration, shared session or proposal in progress; or the setting of D2 is on. | DASHPAY §5a: "appears when the wallet holds masternode keys or a collateral, or in advanced mode". | D2 | Add one toggle, **Settings ▸ General ▸ Show Masternodes** (default off), instead of a general "advanced mode". | No advanced mode and no Advanced tab exist (U-04 D1: General, Security, Wallets, Backups, About). dash-qt has separate per-tab toggles (`fShowMasternodesTab`, `fShowGovernanceTab`), and one item needs one toggle. | D41 | A shared registration's network fee is split by share; the locked terms show each participant's part, and the invitation says so. *f1:* the collateral output must be exactly 1,000 Dash, so each participant funds share **plus** fee part. Each wallet reserves share + maximum, and the Join button names the total ("Join: reserve 300.0001 Dash"). The locked terms state the real fee and each part (≤ the maximum); unused fee comes back as change. If the estimate before Lock terms exceeds a maximum, the coordinator re-invites with a higher maximum and everyone joins again ("The network fee went up…", "Join again: reserve 300.0003 Dash"). A per-participant maximum lets a wallet reserve before the exact fee is known, and a re-invitation (not a silent top-up) keeps "nobody pays more without agreeing". |
| D42 | Owner, collateral, operator's share and registration height come from the ProRegTx; operator and voting keys are always read live from the list. The current **payout address and payees** are known only after the wallet applies every later ProUpRegTx (ProUpShareTx for a shared masternode) for that ProTx hash up to the tip. The wallet watches each known ProTx hash through compact filters from the registration height (Core's filter carries the ProTx hash of every update type), including after a restore. Until that check reaches the tip the payout reads "Checking…", payout custody reads "Payout address: checking", and the withdraw sheet offers no fixed destination ("Checking the current payout address…", Withdraw off). Once checked the help says "checked up to block N". *f2:* the same scan applies ProUpServTx, ProUpRevTx and ProUpSharedRegTx too, in block order and read only: the operator's share is paid once a ProUpServTx sets an operator payout address, and Core clears that address on every ProUpRevTx and every operator-key change (ProUpRegTx or ProUpSharedRegTx), so all of them decide whether it is paid (D46). | Sol r1 #1: the SPV list carries no payout, so a ProRegTx the wallet built can be stale after a ProUpRegTx from another device or the owner's earlier wallet; withdrawing to a stale payout address sends credits to someone else's key. Matching by ProTx hash (not by a wallet key in the payload) also finds updates that move the payout out of the wallet. The operator and voting keys a ProUpSharedRegTx changes come live from the list, but the scan still applies it (see f2). |
| D43 | A tracked masternode whose collateral outpoint isn't known yet gets an **outpoint unresolved** state ("finding its collateral"). The wallet finds the ProRegTx from the list entry's `confirmedHash`, the block at registration height + `nMasternodeMinimumConfirmations`. It looks that hash up in its **verified header chain**, subtracts the network's `nMasternodeMinimumConfirmations` (**15 on mainnet, 1 on testnet**, devnet and regtest), downloads the block at that height from a full-block peer, checks it against the verified header (hash, merkle root) and takes the transaction whose txid equals the ProTx hash. **Outpoint, per Core:** if the payload's collateral hash is null (collateral created in the ProRegTx: FundNew and every shared registration), it is (ProRegTx txid, payload index), and the wallet checks that output's amount (1,000 Dash, 4,000 for an evonode) and script (a single address, or the shared-collateral template); otherwise the payload outpoint as given. Votes are mapped by that derived outpoint (MG-02). Then D42 runs from that height. A masternode not yet confirmed waits; a failed check counts as a failed lookup. Such rows aren't eligible to vote and are never preselected ("Key you added · finding its collateral first"); on failure: "Couldn't find this masternode's registration.
