# DP5-01: Link intake, vault stash, replay, log redaction

ROADMAP DP5-01 (engine, T0): [DASHPAY §2.9](DASHPAY.md)'s last row, "a link opened before any wallet exists survives
onboarding", and §3.8's redaction rule. U-01 routes links (OS deep link → single instance → `take_links` /
`route_link`, its D1–D24) but drops them when no wallet can act on them; its D4 hands an invitation to the renderer
bare and leaves "the intake and the stash" to this task. Here the app keeps payment, contact and invitation links in
the vault's link stash, offers them again after onboarding or unlock, and every log sink redacts links. DP5-02 (claim)
and DP5-03 (its UI) take invitations from the stash by id.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Three kinds are stashed, as the engine classifies them with `dw_uri::deeplink::classify_link` (never on the host's word): **payment** (`dash:`/`pay:` with an address, `dashwallet://pay=…`, a BIP73 string), **contact** (`dashpay://user?…`, DP2-03) and **invitation** (`dashpay://invite?…`, `https://invitations.dashpay.io/applink?…`, an AppsFlyer OneLink wrapping either, as the Android and iOS wallets accept them). Every other link (scan-QR, address requests, DashConnect, integrations, BIP70, a payment without an address) routes as in U-01 and is never stashed. | The kinds the mobile wallets act on after onboarding; the rest have no meaning without a live request. |
| D2 | When: an **invitation** is stashed at intake, always (OS link, second instance, Open URI), because it is a bearer secret that must not travel to the renderer and DP5-02 claims it by id. A **payment or contact** link is stashed only when the window's network has no wallet (`wallet_infos()` empty); with a wallet it routes at once, as before. If its stash fails it still routes. | Survives onboarding (the acceptance) without changing U-01 routing when a wallet exists. |
| D3 | Intake path: OS deep link / launch argument → single instance (U-01) → dw-app `Inbox` → `take_links` / `route_link` → `links::intake` → `NetworkSession::stash_link` → `Vault::stash_link`. Without a session (no network open yet) a launch link waits in the inbox until `take_links` (U-01 D3); an invitation taken while no session of the window's network exists stays queued, in order, for the next `take_links` (review r1 #8; the queue stays bounded: links delivered meanwhile past 16 are dropped, newest first). Nothing announces `linksPending` when a network opens later: the renderer opens its network before it mounts the bridge, so its first take has the session (a requeue needs a failed open; F6); one whose stash fails is refused as `notSaved`, never routed bare. A link that fails to route is rejected alone (`notALink`); the batch goes on. The routes gain `saved {link}` and `invitation {linkId}` (the text is gone from both) and the refusal `notSaved`. | One engine entry; the renderer never holds an invitation's text. |
| D4 | Storage: one file per link, `<vault dir>/links/<id>.dwl` (0600, dir 0700), JSON with version, id, kind, stashed-at, expires-at and either a sealed body or, D6 only, the text. Ids are 16 random bytes in lower-case hex; any other id is `invalid_argument`. Writes go through a temporary file, rename and a directory fsync. The vault manifest is not touched. | Survives restart; no vault record (a record would need the DEK and would block `destroy`'s empty check and the NoKeys states). |
| D5 | Encrypted at rest with ECIES to a **stash key**: secret = HMAC-SHA256(DEK, "dw-vault/link-stash/v1" ‖ vault id ‖ network ‖ counter), the first counter giving a valid secp256k1 key; its public key is kept in `links/stash.pub` with the vault id. A link is sealed with an ephemeral key: ECDH (DIP-15's `ecdh`), entry key = HMAC(shared, "dw-vault/link-key/v1" ‖ ephemeral ‖ stash public), then the vault's XChaCha20-Poly1305 `seal` with AAD over the entry version, vault id, network, id, kind, both times, key id and ephemeral key. So a link can be sealed while the vault is **locked** (from `stash.pub`) and opened only with the DEK (unlocked, mixing-only, or the NoKeys/Unencrypted states that hold it in the clear). | The vault is locked most of the time a link arrives; the DEK stays the only secret. AAD binds every field, so a swapped kind or time is "tampered". |
| D6 | Before a vault exists (no DEK, no `stash.pub`) the text is kept in the clear in its 0600 file, as §2.9 says ("a 0600 file before a vault, moved into the vault at creation"). `create_vault`, `unlock` and `recover_with_mnemonic` reseal every plaintext entry at once with the key they just installed, still holding the writer (D23; failures warn and are retried at the next stash call). A reseal writes and fsyncs the sealed file, renames it over the plaintext one and only then zeroes the old file through a handle kept across the rename, so a crash leaves one of the two (review r1 #3). The same fallback is used when `stash.pub` is missing or names another vault. | The spec's own rule; deviation from the brief's "vault record" wording recorded here. |
| D7 | Bounds: at most 16 entries and 4096 bytes of trimmed text per link (an empty or longer one is `invalid_argument`); a full stash evicts the oldest payment or contact first, then the oldest invitation, never refusing a new link (so 16 invitations opened after a real one push it out: each needs a click, F3). Entry files over 16 KiB are deleted unread. | A link storm from a hostile page cannot fill the disk or wedge intake; the newest link is the one the user just opened. |
| D8 | TTL: payment 7 days, contact and invitation 30 days, from the stash time. Expired entries are deleted on every read. | Payment requests are short-lived; invitations last as long as the mobile wallets keep theirs. |
| D9 | Dedupe: the same text (after trimming) of the same kind returns the existing entry and its id. The comparison uses an HMAC under a process-random key over the opened text, held only in memory, so no file carries a link hash; locked-sealed duplicates are collapsed at the next unlock. | Opening a link twice offers it once, without an offline-checkable hash on disk. |
| D10 | Consumed exactly once: `take_stashed_link` deletes the file (a plaintext one zero-overwritten first, D18; a sealed one just unlinked) **before** returning the text; a second take is `None`. A sealed entry taken while locked is `platform.signer_unavailable` and stays; a plaintext one (kept before a vault) needs no key and is taken. The vault checks the kind under its mutex before opening anything (review r1 #6): an invitation is never handed back nor opened: the engine answers `TakenLink::Invitation` in every lock state, which `open_stashed_link` routes by id (r2 nit 3 replaced an error-detail match); it stays until `forget_invitation` / `forget_stashed_link` (dismissed) or DP5-02's claim. Undecryptable or tampered entries are deleted and read as `None`. | Replay cannot repeat a payment; the secret never leaves the engine. |
| D11 | Replay: after onboarding finishes, after an unlock and at launch, if `stashed_links` is not empty, the renderer shows a "Links you opened" sheet once per run: each row's kind and when ("Payment request", "Contact", "Invitation", "Opened 2 hours ago"), with Open, Remove and Later. Open on a payment or contact takes it and routes it as U-01 does (the pay screen, Add Contact); on an invitation it routes `invitation {linkId}` to Join DashPay, unconsumed. Remove forgets it (`forget_stashed_link`: any kind, unopened, works locked; review r1 #7). Later closes the sheet until the next launch, unlock or onboarding. | The mobile wallets replay the pending link after setup; one quiet offer, never automatic payment. |
| D12 | Refused: links of other kinds (D1) are not stashed; a payment without an address; text over 4096 bytes or with a control character (a line break inside a link would defeat D14); text the redaction does not cut from its first character (D14: a BIP73 `https` payment string, `dash::…`), which still routes, unstashed; malformed ids; a take or forget of an id of another kind (`invalid_argument` / `invitation.invalid`); taking while locked. A stash failure for an invitation is `notSaved` ("This link could not be saved. Open it again after setting up your wallet."). | Attacker-supplied text gets no new behaviour. |
| D13 | Contract: m4 §2.9 gains `stash_link`, `stashed_links` and `take_stashed_link`; `stash_invitation`, `pending_invitations` and `forget_invitation` are implemented on the stash (`invitation_status` stays a stub until DP5-02). No new §4 code (existing `invalid_argument`, `invitation.invalid`, `platform.signer_unavailable`, `vault.*`), so no Swift `engineCodes` change; the surface changes, so Contract-Version 29 and the Swift T0 suite. | m1–m4 contract steps. |
| D14 | Redaction: `dw_uri::redact::redact_links` cuts a line at its first link and replaces the rest of the line with `<link>`. A link starts at a link scheme (`dash:`, `pay:`, `dashpay:`, `dashwallet:`, `dash-key:`, `dash-st:`; case-insensitive; not after a letter, digit, `+`, `-`, `.`; not a Rust path such as `dashpay::overlay`) or at a token naming an invitation host (`invitations.dashpay.io`, OneLink/AppsFlyer) or a secret or payee parameter (`pk=`, `dapk=`, `assetlocktx=`, `islock=`, `du=`, `deep_link_value=`, `dashpay%3a`). Only the end of the line ends a link: the parsers accept quotes and brackets inside one (the fuzz seeds found `dash:x"?label=…` leaking past a quote), and the stash refuses text with control characters (D12), so a kept link is one line, and the stash keeps only text that `redacted_whole` reads as a link from its first character (the fuzz run found `dash::<address>`, which a parser takes for a payment and the redaction for a Rust path). Every log sink goes through it: dw-app's `DW_LOG` subscriber and dwcli's `DWCLI_LOG` (a `RedactingWriter` per event), the two `eprintln!` sites that can echo input (launch argument errors, refused navigation), and the self-test link trace (`Shell::trace`; it held no link text before, U-01 D16, but its `routed` lines are renderer-supplied). The engine never logs link text (errors carry codes and kinds only). Two more paths (review r1 #1, #2): a terminal escape sequence (`ESC[…m`, a coloured log's field `name=`) delimits tokens whole, so its final letter never hides the scheme after it, and both subscribers log without colour anyway; a panic message may quote a link, so dw-app (always) and dwcli install `redact_panics`, a hook printing the thread, location, message and any backtrace through `redact_links` (dwcli's DashPay commands keep withholding the message). The test plants an invitation secret, an address, an amount and a username, runs intake and routing with tracing at `trace` in a child process, logs a link as a message, as a field and in a caught panic, and greps its stderr, stdout and the trace for each (and for escape codes). | §3.8 and the acceptance's redaction test; cheap enough to run on every log line. |
| D15 | Parser fuzz seeds (T0): a proptest target over `classify_link`, `normalize_invitation`, `DashPayUserLink::parse`, the contact-code parser and `redact_links`: no panic on any input, classification ignores surrounding whitespace, and the payee, username, identity, invitation, or any parameter value as written or decoded (`pk`, `du`, `assetlocktx`, amounts) of a kept link never survives redaction, whatever text surrounds it (a coloured field among the surroundings). Seeds in `testdata/link-corpus/` (each kind, the mobile wallets' examples, edge cases) run every time; the generated cases are bounded (256) so the gate's run is seconds. H-02 can feed the same corpus to cargo-fuzz. | T0 asks for seeds and a bounded run, not a farm. |
| D16 | DP5-02/03 hook: the stash id is the claim's handle (`RegistrationFunding::Invitation { link_id }`); DP5-02 adds an engine-internal read of an invitation's text by id (never to the host) and calls `forget_invitation` after the claim. | The claim link replays into DP5-02/03 without a new store. |
| D17 | `recover_with_mnemonic` makes a new DEK: entries sealed to the old stash key cannot be opened and are deleted at the reseal (plaintext ones are sealed to the new key). `destroy` removes the whole stash before the vault file, holding the writer lock and then the stash mutex until the vault is gone from memory (order: writer, stash mutex, gate), so no stash call seals to the destroyed key meanwhile; without a vault it removes the plaintext entries kept before one ("Delete All"; review r1 #4). A recovery deletes the old key's links without telling the renderer (F4). | Nothing undecryptable lingers; destroy leaves no link behind. |
| D18 | Deletion overwrites the file with zeros and fsyncs before unlinking; on copy-on-write or journaling file systems this is best effort, which is why the text is sealed whenever a stash key exists. | Honest about secure delete. |
| D19 | `stash.pub` is not authenticated: a local attacker who can write it could make new links seal to their key. Every unlock rewrites it from the DEK and drops entries sealed to another key; the threat (a writer in the vault directory) is outside the vault's model (E0-08 §threats). | Bounded exposure, recorded. |

| D20 | Copy (mobile wallets' tone): the toast "Link saved. It opens once your wallet is set up." for a kept payment or contact link; an invitation during onboarding "Invitation saved. It is waiting for you once your wallet is set up."; after onboarding it opens Join DashPay, whose note now says "Dash Wallet keeps it for you under Links you opened; joining with an invitation is not available yet." (DP5-03 replaces it). A sheet row is the kind ("Payment request", "Contact", "DashPay invitation") and "Opened 5 minutes ago", newest first; an entry gone meanwhile is the toast "This link is no longer saved." | The window never shows a link's text, so nothing to redact in the UI either. |
| D21 | The sheet is a shell dialog (`dialog: "savedLinks"`), so the shell's rules hold: dropped while locked, onboarding or behind a sheet, the shell inert behind it. The offer fires once per trigger (launch, onboarding done, each unlock) and only when `stashed_links` is not empty; the sheet re-reads the list each time it opens (`gcTime: 0`), since links arrive and expire without an event. | No new modality rules; no stale rows. |
| D22 | CI's OS deep-link job (`ci/github/deep-links.sh`) runs on a fresh profile, which has no wallet: its payment and contact links now route as `saved` (they used to route as `pay` / `addContact`), and it also opens an invitation (`routed invitation`) and greps the trace and the app's log for the planted address, identity and invitation key. | The OS-level half of the acceptance, on every platform CI runs it. |
| D23 | The reseal after `create`, `unlock` and a recovery is not a gated operation: it derives the stash key from the data key the call just installed and runs before the call releases the writer, so no recovery (a new key and vault id) or destroy can run between the install and the reseal (r2 M1: a reseal after the writer went could restore a stale `stash.pub` and delete links sealed to the new key). It opens no sealed entry (it seals plaintext entries, rewrites `stash.pub` and drops entries under another key id; dedupe and the tamper check wait for the next gated stash call) and hands nothing to any caller, so a `lock()` meanwhile has nothing to stop (a gated reseal would add a logged release per unlock, which `lock_race_tests` counts). Every other stash call loads an unencrypted vault's key from the OS store **before** taking the stash mutex (the store may block on a keyring prompt; review r1 #5) and on failure goes on as if locked: a new link is sealed to `stash.pub`. Lock order: writer, stash mutex, gate. | Gate semantics unchanged; a slow keyring never holds the stash. |
| D24 | `stash_invitation` checks the text with the invitation parser alone (`normalize_invitation`, its copy zeroed) before the full classification: text handed in as an invitation is a bearer secret, and the payment parser keeps unzeroed copies of what it reads (dwcli's heap test caught `dash:?invite=…` freeing an unwiped copy). The full classifier is not run on it at all (r2 nit 5; its `uphold` branch copies the text). Best effort still: `normalize_invitation` percent-decodes a OneLink payload into unzeroed temporaries, as U-01's intake path does. | The secret path parses as little as it can. |

## Follow-ups

- F1: Add-wallet onboarding (a second wallet) does not stash payment/contact links (D2 checks for any wallet).
- F2: DP5-02's engine-internal invitation read and claim (D16); DP5-03's UI replaces the sheet's invitation row's Open.
- F3: A per-kind cap (or a user-confirmed invitation) so a burst of invitation links cannot evict one the user wants (D7).
- F4: Tell the renderer when a recovery dropped links sealed to the old key (D17); and drop a stashed payment when the same link is opened again with a wallet (it routes at once and the stashed copy waits until its TTL).
- F6: Announce `linksPending` when a network opens with links queued (D3), should a flow ever open the network after the bridge mounts.
- F7: A directory left at an entry's temporary name (`<id>.tmp`) blocks that entry's reseal until removed (the plaintext entry stays whole; local-only).
- F5: Windows: the stash files rely on the vault directory's ACL (dw-fs), as the vault file does; no extra ACL is set per entry. The reseal renames over a file it still holds open (to zero it after), which Rust's default `FILE_SHARE_DELETE` allows; `sealing_never_loses_the_plaintext_entry` on Windows CI checks it.
