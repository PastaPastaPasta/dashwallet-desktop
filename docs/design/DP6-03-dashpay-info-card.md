# DP6-03: the DashPay card in Tools ▸ Information

ROADMAP DP6-03 (size S, UI, tier T0, engine review N). DASHPAY F23 (iOS Sync Info, IOS-114/139) puts a DashPay card
in Tools ▸ Information: the loops, the last pass, pending contact crypto, the scan verdict, the quorum source and
"Sync now". It replaces U-05's "not yet (DP6-03)" row. Its sources are E0-05 (the bring-up outcome and the loops),
E0-10b (the quorum source and the degraded mode, DEC-168) and BL-153 (`DashPay.status`). Every value comes from
generated IPC types in `apps/desktop/src/api/generated/`. The task adds no engine call, no app command and no binding.

## 1. Fields

| Row | Source (facade → command → generated type) | Format |
|---|---|---|
| State chip and headline | `dashpayInfo` over all the reads below (§2) | a chip (`chip-success` / `-neutral` / `-warning` / `-danger`) and one line; a second line explains, where needed |
| Identity scan (the scan verdict) | `DashPay::sync_status().startup` → `dashpay_sync_status` → `DashPaySyncStatus.startup` (`StartupStatus`, the bring-up outcome, DASHPAY §3.2) | one text per outcome (`STARTUP_TEXT`), e.g. "Complete: identity found", "Failed: discovery did not finish", with a note where the user can act or wait |
| Last pass | `DashPaySyncStatus.lastPass` (`SyncPassReport \| null`) | "—" with "No pass has reported yet." while `null` (always today, D4); else its end as the tab's dates ("Tue Oct 6 11:59:55 2026") and "2 new requests, 1 new contact", "Nothing new" or "Failed: <code>" |
| Contact accounts waiting to be built (pending crypto) | `DashPaySyncStatus.pendingContactCrypto` (the bring-up's `contact_accounts_pending`: builds waiting "for an unlock or the DIP-15 rescan", startup_status.rs) | "None", else the count with "They're built after an unlock or the DIP-15 contact rescan." |
| One row per loop | `DashPaySyncStatus.loops` (`SyncLoopStatus[]`, `NetworkSession::platform_loops`, engine order) | "Running · last run 11:59:55 · next 12:00:10", "Running · no run yet", "Stopped · last run …", "Stopped"; today's times as HH:MM:SS, older ones as the tab's dates (D9) |
| Quorum keys (the quorum source) | `DashPaySyncStatus.quorumSource` (`QuorumSource`); without a wallet `NetworkSession::quorum_source` → `quorum_source`; the toggle `NetworkSession::trusted_quorums_only` → `trusted_quorums_only` | "SPV (verified masternode list)"; "Trusted service until masternode sync finishes" (data unverified); "Trusted service (degraded mode)" (compared with SPV where it holds the quorum); "Trusted service only (developer setting)"; with the toggle's read failed, "Trusted service" with "Could not read whether SPV checks of quorum keys are off." (D5) |
| Whether the wallet has an identity | BL-153 `DashPay::status` → `dashpay_status` → `DashPayStatus`, the shell's query (`useDashPayShell`, key `["dashpay", "status", walletId]`) | not a row: it decides Watch-only, Not set up and Starting (§2) |
| Sync now | `NetworkSession::dashpay_sync_soon` → `dashpay_sync_soon` (D3) | a small tinted button in the card's header; held, with the reason under the headline, while it would do nothing: no identity known, the bring-up still running, the DashPay loop not running, or a watch-only wallet (D3) |

## 2. States

`dashpayInfo` takes the first that applies (D2):

| State | When | Chip / headline | Sync now |
|---|---|---|---|
| `noWallet` | no wallet on the network | neutral "No wallet" / "No wallet on this network yet"; the quorum row alone, from `quorum_source` | none |
| `error` | `dashpay_sync_status` failed and nothing was read | danger "Unread" / "Could not read DashPay's sync state", the reason, Try again; no rows (D7) | none |
| `loading` | not read yet | neutral "Reading" with a spinner | none |
| watch-only (`watchOnly`) | the wallet's summary says `watchOnly`, or the status is `noIdentity{watchOnly}` | neutral "Watch-only" / "DashPay needs this wallet's keys" (DP1-08's copy); no second line, the held button's reason says why | held: "A watch-only wallet can't use DashPay because it has no keys." |
| failed (`failed`) | the last pass reported a `failureCode`; or, while no identity is known and none is proven absent, the bring-up ended `discoveryFailed`, `identityScanIncomplete`, `partialNoIdentity`, `partialAccountsPending` or `seedBindingUnverified` (the Home card's failure set, status.ts) | danger "Failed" / the Home card's "Could not finish looking for your DashPay identity" or "Could not confirm your DashPay identity", or "The last DashPay pass failed" with "It stopped with <code>." | a failed bring-up: held, "Sync now waits until DashPay finds this wallet's identity."; a failed pass: as the loop allows |
| not started (`notStarted`) | no identity known or proven absent, and the bring-up did not run (`notRun`) | neutral "Not started" / "DashPay has not started" | held, "Sync now waits until DashPay finds this wallet's identity." |
| starting (`starting`) | no identity known or proven absent (the status is `startupIncomplete`, BL-153 D16, or unread with any outcome but `ready`), and the bring-up runs (`starting`, with a spinner) or waits for an unlock (`identityUnsettled`) | neutral "Starting" / "Looking for your DashPay identity…" or "Unlock to look for your DashPay identity" | held, "Sync now waits until DashPay finds this wallet's identity." |
| starting, identity known (`starting`) | an identity, the bring-up running (`starting`) and the DashPay loop not running yet: every launch, since the bring-ups run before SPV and the loops start (D19) | neutral "Starting" / "DashPay is starting", with a spinner | held, "Sync now waits until DashPay has started." |
| not set up (`notSetUp`) | the status is `noIdentity` (`null` or `waitingForSync`). This beats a `notRun` outcome: a wallet whose `no_identity` marker is fresh skips the bring-up (D15) | neutral "Not set up" / "No DashPay identity on this wallet", "Join DashPay to create a username." (or "…once the wallet has synced.") | held, "Sync now waits until this wallet has a DashPay identity." |
| stopped (`stopped`) | an identity, and the DashPay loop does not run (SPV stopped, or Platform not started) | neutral "Stopped" / "DashPay sync is stopped" (D16) | held: "DashPay's sync loops are not running. They run while the wallet is connected to the Dash network, and can take a little while to start after it connects." |
| degraded or fallback (`degraded`) | an identity, the DashPay loop running, quorum keys not from SPV | warning "Degraded" / "Quorum keys from a trusted service", "Trusted quorum keys until masternode sync finishes" or "SPV quorum checks are off (developer setting)"; the quorum row's note says more | enabled |
| running (`running`) | an identity, the DashPay loop running, quorum keys from SPV | success "Running" / "Quorum keys verified by SPV" | enabled |

All states but `noWallet`, `error` and `loading` show every row. Each has a fixture scenario (`src/fixture/tools.test.ts`
checks it end to end): `dashpay-info-spv` (running, a pass report, two contact accounts waiting),
`dashpay-info-identity-incomplete` (running: an identity with a `partialAccountsPending` outcome, the common real case
for contact accounts waiting), `dashpay-info-bringup-running` (an identity, the bring-up running, the loops not yet
started, D19), `dashpay-registered` (degraded,
the default quorum source), `dashpay-info-fallback`, `dashpay-info-trusted-only`, `dashpay-info-pass-failed`,
`dashpay-look-failed`, `dashpay-starting`, `dashpay-identity-unsettled`, `dashpay-not-started`, `funded` /
`dashpay-no-identity`, `dashpay-info-no-identity-proven` (the `noIdentity` status with a `notRun` outcome, D15),
`dashpay-waiting-for-sync`, `dashpay-watch-only`, `no-wallet`, and `dashpay-info-stopped` (SPV stopped: the loops stop
and Sync now is held).

"An identity" is the status's `ready`, `registering` or `contestPending`. With the status unread, the outcome alone
decides: `ready` is an identity, anything else (`noIdentity` too, BL-153 D16) is the bring-up's progress (D2). A failed read is `fail=dashpay_sync_status:<class>`
(or `list_wallets`, `trusted_quorums_only`). The two scenarios with a `lastPass` (`dashpay-info-spv`,
`dashpay-info-pass-failed`) are forward-looking: no engine reports a pass yet (D4, F2), as `scenarios.ts` says.

## D-rows

| # | Decision | Why |
|---|---|---|
| D1 | The card reads `dashpay_sync_status` and the shell's BL-153 status query (same key, same cache), plus `trusted_quorums_only`; `quorum_source` only without a wallet (with one, the sync status carries the source). The wallet is the toolbar's (`ui.walletId`, else the first), as Settings' DashPay card picks it. No engine call, command or binding is added: all four commands were bound by E0-13/E0-10b. `dashpaySyncSoon` already had a `Backend` method; the other three gain one. | The brief: reuse BL-153's status rather than a second status path; generated IPC types only; adding engine API is out of scope for a UI row. |
| D2 | The precedence of §2. Watch-only first, from the wallet's summary as well as the status (nothing else can change for a wallet without keys). Then a failed last pass, which the user may need to act on even with an identity on file. Then, only while no identity is known and none is proven absent, the bring-up's own failure or progress: once BL-153's status says `ready`, a stale failed outcome (a scan that failed, then a lookup that found the identity) no longer decides. Then no identity, which beats stopped and degraded (without an identity nothing of the user's is synced or verified, and the rows still say where things stand). Then a known identity's bring-up still running with the loops not yet started (Starting, D19). Then stopped, degraded, running. The failure set is the Home card's (`startupCard` in status.ts), so the two surfaces never disagree. With the status unread the outcome decides alone: only `ready` counts as an identity, so an unread status never makes a wallet look healthy, and its `noIdentity` counts as no absence either (the bring-up's `NoIdentity` proves none, BL-153 D16), so the card says "Looking…" as it does for `startupIncomplete{noIdentity}`. Only BL-153's status proves an absence. | The brief's six states, each with one place in the order; consistency with DP1-08. |
| D3 | "Sync now" calls `dashpay_sync_soon` (E0-05's pass-now entry: a DashPay pass and the balance pass, in the background; nothing while the Platform loops are stopped; a pass in flight is not repeated). `DashPay::sync_now`, which would return the pass's report, is still a `platform.not_implemented` stub (startup.rs), so the card does not call it and no API was added. The button is held, with the reason as its `aria-describedby`, wherever the kick would do nothing for this wallet: while the DashPay loop does not run, for a watch-only wallet, while no identity is known (failed, not started, starting, not set up: a pass syncs a known identity's contacts and payments and never looks for an identity, which the next start does), and while a known identity's bring-up still runs (D19). A failed pass follows the loop rule only with an identity known. Two edges are accepted: with BL-153's status read failing for a wallet with an identity and an incomplete outcome, Sync now is held as if none were known (the status read is in memory and a failure is transient); and a `registering` wallet counts as one (D2), so Sync now is offered while the pass has nothing of this wallet's to sync yet, which is harmless since the pass is session-wide. The engine's own check is the Platform supervisor (`platform.is_running()` and `loops_on`, runtime.rs `kick_dashpay_sync`); the card has only the loop's `running` (`platform_loops`), which the supervisor starts and stops with it, so the two agree except for an instant around a start or stop, where the click is harmless. It uses the native `disabled` attribute, as every held button in the app does, so the reason is read from the note under the headline. Since the kick reports nothing, the card says so plainly: "A DashPay pass was asked for. It runs in the background. Passes don't report their results yet, so this card may not show when it ends." It reads itself again once, 5 s later (`SYNC_NOW_REREAD_MS`), which shows the contacts loop's new last run if the pass ended by then (the library sets it at the pass's end); a pass that finds news also sends its Platform signals (D6). It promises nothing more: a pass over many wallets routinely takes longer. | The brief: use the existing cadence entry, add none. A disabled button with its reason (DASHPAY §3.2's watch-only wording) is more honest than a click that does nothing. |
| D4 | `last_pass` is `None` until sync passes report (E0-10b §7, m4 §2.1), so today the row always shows "—" and "No pass has reported yet.". The formatter and the failed-pass state are built and tested on fixture reports anyway, so the card needs no change when the engine fills the field. | The contract's field exists; the card shows what the engine has. |
| D5 | `QuorumSource::Trusted` is both the default degraded mode (DEC-168) and the developer toggle, so the card also reads `trusted_quorums_only` to tell them apart. While the toggle is unread the card assumes the default, the degraded mode. Every source other than `spv` is the degraded state. Until H-09 turns on enforcement, every wallet with an identity therefore shows "Degraded" (E0-10a failed, DEC-168). The headline names the source in one line and the quorum row's note says what it means; there is no second line repeating it. When the toggle's read failed the card claims neither: the headline is the source's own ("Quorum keys from a trusted service", true of both), and the row says "Trusted service" with "Could not read whether SPV checks of quorum keys are off." | The truth, as m4 §2.2 describes it; the toggle changes what "trusted" means for the user's data. |
| D6 | The sync status's query key is `["dashpay", "syncInfo", walletId]`, under `["dashpay"]`, so every `platform` and `dashPayNews` event re-reads it (events.ts). Sync events (`spvStateChanged`, `sync`) re-read every wallet's sync status too: events.ts invalidates `["dashpay", "syncInfo"]` with the sync and status keys, because the loops start and stop with SPV and send no Platform signal. Invalidating every wallet's entry, not the shown one's, means a wallet switch never shows another moment's loops from the cache. `useReloadOnSync` re-reads only the session's quorum source, used without a wallet. The loops start (`start_loops`, retried while an old pass drains) and run without any signal, so the sync status is read afresh each time the card is shown (`refetchOnMount: "always"`, a memory read in the engine). Nothing polls (DASHPAY §3.5). The loops' times are those of the last read. | Hosts re-query on signals and never poll; sync events come at most 4 Hz. |
| D7 | A failed `dashpay_sync_status` read, or a failed wallet list (which would leave nothing to read), shows the reason and Try again, and no rows: nothing is guessed. Try again re-reads whichever failed. A read card stays as read when a later refetch fails (TanStack keeps the data; the error shows only while the sync status is unread).
