# U-03: Home, Pay, Receive, Activity (Tauri)

ROADMAP U-03 for the Tauri renderer: the wallet's everyday screens on the E0-13 commands. The
layout follows the mobile wallets (Dash iOS and Android) with the dash-qt facts that desktop users
expect (UX-SPEC §4.5, §4.7–§4.9, §5). Pay ▸ To a contact stays with DP3-06; Tools ▸ Coin
Selection and the address book with U-05; display units and decimal digits with U-04's Options.

## The send flow

```
editing ──Review──▶ confirm ──Send──▶ authorize ─▶ draftPrepare ─▶ check summary ─▶ draftBroadcast ─▶ result
   ▲                  │ Cancel            │ wrong passphrase / credential_required: stay in confirm
   └──────────────────┘                   └ any other failure ─▶ result (failed), the form is kept
```

1. While the user types, the page keeps one engine draft (`newTxDraft`, made on the first
   estimate) and sets its recipient, coins, fee and change, then `draftEstimate`s it: 300 ms after
   the last change, latest wins. The estimate's fee and the engine's refusals (`send.*`) show
   under the form, a recipient's one at its field.
2. Review opens the confirm sheet from that estimate. It names the full address, the amount, the
   network fee and the total that leaves the wallet (`totalSent + fee`).
3. Send asks the vault for a `spend` grant capped at that total (`authorize`), signs
   (`draftPrepare`), checks the prepared transaction against what the sheet showed (same address
   and amount, total within the cap), and broadcasts it (`draftBroadcast`). The engine refuses a
   prepare that would take more than the grant (`send.grant_exceeded`), so the confirmed total is
   binding even if coins moved between estimate and prepare.
4. The result sheet replaces the confirm sheet.

## D-rows

| # | Decision | Why |
|---|---|---|
| D1 | Pay ▸ To an address pays one recipient, as iOS and Android do. The engine's draft takes a list; dash-qt's "Add Recipient" is not built. | The desktop follows the mobile wallets; one recipient keeps the confirm sheet and the result plain. A many-recipient payment is a PSBT or console job until a task asks for it. |
| D2 | Confirm first, then authenticate, then sign and send (the flow above). The grant's `maxDuffs` is the confirmed total; after `draftPrepare` the renderer compares the prepared summary with the confirmed one (every output is the payment to the confirmed address in the confirmed amount, or change to the confirmed change address or the wallet's own; `totalDebit` ≤ cap) and abandons it (`draftAbandon`) with "The payment changed. Review it again." if they differ. | iOS and Android confirm, then ask for the PIN. Capping the grant at what the sheet showed makes the confirmation binding in the engine, not only in the renderer. |
| D3 | The payment-authentication policy (E0-13 D11) decides the credential, never the renderer alone: the sheet asks for the passphrase when the vault is encrypted and `paymentAuthentication` is on or unknown (a failed read counts as on). Otherwise it presents `unencrypted` (an unlocked vault). If the engine answers `vault.credential_required` anyway (the setting changed meanwhile), the sheet shows the passphrase field. A wrong passphrase stays in the sheet with the vault's attempt count and wait. The passphrase is cleared after every attempt. Quick unlock is not offered. | The engine enforces the rule; the renderer only picks the prompt. Erring towards asking never weakens the policy. Quick unlock needs an OS biometric store, which only macOS has (E0-13), and U-04 owns its settings. |
| D4 | No 3-second countdown on Send (dash-qt `SEND_CONFIRM_DELAY`). When no passphrase is asked, Cancel takes the focus once the payment policy has loaded, so Return in the sheet cancels; when one is asked, the passphrase field has it and Return sends only with it typed. Send is a separate filledBlue button. | Mobile sheets send at once. Focusing Cancel keeps a stray Return from sending, which is what the delay guards against. |
| D5 | Live estimate: 300 ms debounce, latest wins (the estimate is a query keyed by the whole draft spec, so an older answer never shows; the draft's writes run one at a time, so an estimate never reads another's half-set draft). Refusals map by code to dash-qt's send-dialog strings (`pay/model.ts` `sendErrorText`); one that carries a recipient index is shown at the address or amount field. | One place for send copy; the engine already says which field is wrong. |
| D6 | Draft lifecycle: one draft per Pay page and wallet, made lazily, closed through `api/send.ts` `closeSendDraft` when the page unmounts, the wallet changes or the vault locks. If the page's own broadcast is running then, DEC-67's line ("Lock stops new signatures; a transaction already signed may still be sent") shows as a toast (E0-13 D8). A prepared transaction that is not broadcast is abandoned. Closing ends every write queued before it (a generation counter): such a write makes no new draft and fails with `send.cancelled`, so a send or estimate still running when the page, wallet or unlock goes cannot open a draft nobody closes. A signature is never retried on a replacement draft. After a sent payment the draft is closed and the form cleared. | E0-13 D8 assigns draft closing to this screen. Leaving drafts open would hold handles (64 per kind) and, for prepared ones, reserved coins. |
| D7 | Coin control is an "Advanced" disclosure under the form, collapsed by default (mobile has none; dash-qt hides it behind an option). Coins: Any available funds, Fully mixed funds only (CoinJoin), or Selected coins: the wallet's `utxos` with checkboxes and dash-qt's summary (`coinSelectionSummary`: quantity, amount, fee, after fee, bytes, change; "≈" prefixed). Locked, reserved and immature coins are listed but cannot be selected. Fee: Recommended with a confirmation target from `feePolicy.targets`, or Custom DASH/kB between `minRelayPerKb` and `maxCustomPerKb`. Change: automatic or a custom address. "Lock unspent" stays in Tools ▸ Coin Selection (U-05). | QT-067…075 in the place a desktop wallet user looks for them, without crowding the mobile form. Locking coins changes wallet state and belongs to the technical view. |
| D8 | Max asks `maxSpendable` for the chosen coins and fee and turns on "Subtract fee from amount" (dash-qt "Use available balance"). Editing the amount afterwards leaves the box as the user set it. | dash-qt's rule: the fee comes out of the maximum, or the payment cannot be built. |
| D9 | Amounts are typed in DASH and parsed by dw-units (`parseAmount`), never by the renderer; display units come with U-04's Options. Addresses are checked by `classifyAddress` for the window's network: Platform and shielded addresses get their own message. | E0-13 D12: the renderer never re-implements dash-qt's amount rules. |
| D10 | Result: Sent shows the amount, the fee and the transaction id, with Close and Show in Activity (opens Activity with the transaction's detail sheet; dash-qt jumps to the new transaction, UX-SPEC §4.7). `send.broadcast_unknown` keeps the prepared handle (E0-13 D8): "The payment may have been sent" with Try again. Only a first attempt the engine released (`send.no_peers`, `send.broadcast_rejected`, `send.prepared_tx_spent`, `send.cancelled`) or whose handle was already gone (never dispatched) is "not sent", with Back to payment, which keeps the form. Every other broadcast failure, and every failure of a retry, stays unknown and is never abandoned: once a transaction may be on the network the screen must not invite a second payment. If the handle went with the draft meanwhile (a lock), Try again is replaced by "check Activity". | UX-SPEC §4.7 and the engine's broadcast contract. |
| D11 | Receive: the QR encodes `dash:<address>` (`buildPaymentUri`), error correction level L (`qrMatrix`, dash-qt's 255-character cap), drawn as SVG with a 4-module quiet zone and no centre badge (UX-SPEC §4.8). New address = `nextReceiveAddress` (dash-qt `getNewDestination`). Request payment stores a request on a fresh address (`createReceiveRequest`) and opens its sheet (QR of the request's URI, details, Copy link, Copy address); the requested payments list shows Show and Remove (`deleteReceiveRequest`). The iOS live payment watcher is not built (UX-SPEC §4.8: M5). | Mobile receive screen plus dash-qt's request history, as UX-SPEC §4.8 draws it. |
| D12 | Activity filters: the type chips (iOS), a Date menu (All, Today, This week, This month, Last month, This year: dash-qt's list without Range) and a minimum amount (dw-units parse; an unparsable value marks the field and is ignored). They apply in List and Table mode and to the footer count. Weeks start on Monday, dates in the window's locale. | dash-qt's filter bar minus the custom range, which needs a date-picker component no screen has yet. |
| D13 | Table mode: dash-qt's columns (status icon, Date, Type, Address / Label, Amount) as a native `<table>`; the Date and Amount headers sort through the engine (`HistorySortName`), toggling direction. A row opens its detail sheet by click, or by Enter / Space on its focusable Date cell button. List mode stays the default (UX-SPEC §4.9). | Keyboard and screen-reader users get one control per row, not a clickable `<tr>`. Sorting in the engine keeps paging by cursor correct. |
| D14 | A row's title, its table party (address, label) and its leading slot come from one place: `format/tx.ts` `txTitle` / `rowParty` and `components/history.tsx` `TxRowView`'s `decorate` prop. DP3-02 (counterparty attribution) puts the contact there; nothing else in U-03 reads `TxRow.address` for display. | DP3-02 runs in parallel and edits the same rows; one seam keeps the merge to a few lines. |

"Open in Insight" is not built: the webview blocks navigation and the app has no opener plugin yet. | QT-091 and QT-093 where they apply; an explorer link needs an allowlisted opener, which is a security decision for a later task. |
| D16 | Home shortcuts: Receive → Receive; Send → Pay ▸ To an address; Scan QR → Pay ▸ To an address with the address field focused (as U-01 routes a `scanQr` link: the desktop has no camera, and pasting a scanned link there works); Back up stays disabled until the recovery-phrase screens (U-02). An empty history shows [Receive Dash]. | Every working slot leads where its mobile counterpart does. |
| D17 | Drag and drop of a payment link onto the window (QT-019, deferred to U-03 by U-01 D13) is deferred again. | Tauri's native drop handler (on by default) hides HTML drops in every webview; turning it off and routing drops needs a shell change and per-OS checks that are not part of the wallet screens. Follow-up. |
| D18 | The fixture (U-07) models the send engine (`src/fixture/send.ts`): draft and prepared handles (E0-13 D8's drops), the recipient checks, a deterministic estimate (largest coins first; P2PKH size `10 + 148 × inputs + 34 × outputs` bytes at 1 000 duffs/kB; change under dust goes to the fee), `maxSpendable` as the coins' sum, the `spend` grant cap and the payment-authentication rule (`vault.credential_required` for `unencrypted` on an encrypted vault while `World.paymentAuth` is on), reserved inputs, a broadcast that adds a history row and moves the balance, and abandon / resend refusals. `World.send.broadcast` picks `ok`, `unknown`, `rejected` or `noPeers`; as in the engine, a transaction is recorded when handed over (also on `unknown`), never released afterwards (a retry's failure is `broadcast_unknown`, abandon is `send.prepared_tx_spent`, closing its draft keeps its coins spent), and the grant caps outputs the wallet does not own plus the fee, checked after the plan. A locked vault answers `vault.locked`; `credential_required` covers `spend` and `platformOp`. Receive keeps issued addresses and requests. The fixture's `qr_matrix` is a deterministic stand-in, not a scannable code. | Playwright drives every state without an engine; the real QR and amounts are dw-uri's and dw-units', tested in Rust. |
| D19 | Regtest acceptance (ROADMAP U-03) runs the real app on dashd regtest through tauri-driver: `e2e-tauri/regtest-send.ts`, `scripts/e2e-regtest-send.sh`. It funds a new wallet from dashd, unlocks, waits for the balance on Home, pays a dashd address through Pay (Review, passphrase, Send), checks the result, finds the transaction in dashd's mempool with the paid amount, mines it and sees it confirmed in Activity. Not in CI: it needs dashd (`contrib/setup-dashd.py` of rust-dashcore, or `DASHD`). | The acceptance is a real send through the UI; the smoke stays engine-only without a chain. |
| D20 | `docs/parity.md` is left as it is (U-01 D17): the Tauri re-baseline adds U-03's rows (QT-034…040, 052…075, 081…093; IOS-024…031, 040…055) in one pass. | It measures the Swift apps and has no Tauri column. |
| D21 | Change to a custom address counts toward the confirmed total and the grant cap, and the confirm sheet shows "Change to" with the address and amount and says why. Automatic change does not. | The engine counts change to an address the wallet does not own as outflow (`outflow_of`), and the renderer has no ownership check; capping at payment + fee made a foreign change address fail every time.
