# E0-13: the facades bound for Tauri

ROADMAP E0-13 for the Tauri stack (G-04, DEC-190, ADR 0003): `dw-app` commands, generated
TypeScript types and the event bridge. UniFFI `dw-ffi` stays frozen and gains nothing; Governance
and Masternodes are bound later (MG). Code: `rust/crates/dw-app/src/{ipc,api,dto,error,bridge,codegen,coverage}.rs`;
generated files: `apps/desktop/src/api/generated/`; coverage table: [E0-13-facade-coverage.md](E0-13-facade-coverage.md).

| # | Decision | Why |
|---|---|---|
| D1 types | ts-rs 12 writes one `.ts` per record. A command manifest (`ipc::commands!`) declares each command once and also emits its spec (arguments, result, docs, facade claims); `codegen` turns the specs into `generated/commands.ts`: a typed wrapper per command (camelCase name and arguments; every argument required, `null` written out), `CommandArgs` / `CommandResults` maps, `COMMANDS`, `ERROR_CODES`, `ENGINE_EVENT`. The generated files are committed; `codegen::tests::bindings_are_current` fails when they are stale, and CI regenerates them (`DW_UPDATE_BINDINGS=1`) and runs `git diff --exit-code`. | One source per command, so a Rust signature change cannot leave the TS side behind. tauri-specta is still 2.0.0-rc.25 on a pinned rc of specta; ts-rs is what G-01 chose and G-02 used. No argument is optional because a left-out one would mean "none" silently: `createVault()` would make an unencrypted vault, `dropUnconfirmed()` act on every wallet, `setMainName(w, id)` clear the name. `write_bindings` also refuses two Rust records of one TypeScript name (D14). Committed files let the renderer build without Rust and make every binding change visible in review. |
| D2 coverage | Every `pub fn` of `Engine`, `NetworkSession`, `DashPay`, `TxDraft`, `PreparedTx` and `Vault`, read from the dw-engine and dw-vault sources, plus the free functions hosts call (`coverage::FREE`), is either claimed by a command's `#[facade("Type::method")]` or listed in its domain's `EXCLUDED` with a reason, never both. Reasons are `internal: …` (engine plumbing no host calls: signers, paths, closures the binding wraps) or `deferred (MG): …`. `coverage::tests::facades_are_covered` fails on an unclaimed, doubly-listed or unknown method; the table is generated and checked like the bindings. | A facade method added later fails the test until someone decides to bind or exclude it; the reasons are reviewable in one table. |
| D3 events | One Tauri event, `engine://event`, with a typed payload `AppEvent`: a mirror of `EngineEvent` plus the binding's own `eventsOverflowed`. `TauriSink::emit` maps the event to its DTO, offers it to a bounded queue (1024 events, `try_send`) and returns; a dedicated thread emits the queued events. Queued events are DTOs with bounded payloads (below), so the queue's memory is bounded in bytes, not only in count. Order: FIFO across all kinds (one queue, one consumer, one event name). When the queue is full the event is dropped and a flag is set; the forwarder clears it and sends `eventsOverflowed`, coalesced (one for the drops since the last), right after the event it was sending, or within 250 ms when it was idle (it waits for events with that timeout, so a drop recorded after the queue drained is not stranded). The renderer treats it like `sessionOpened`: every query but the network refetches. The network query is left alone because refetching it opens the launch network; the renderer changes the network only by its own `openNetwork` / `closeNetwork` calls (D7), and `activeNetwork` reads it. No event's news exists only in the event. Each one-shot event has a query that reads its state: `sessionOpened`/`sessionClosed` → `activeNetwork`; `walletCreated`/`walletRemoved`/`walletLoadChanged` → `listWallets`; `spvStateChanged`/`sync` → `spvState`/`syncStatus`; `balances` → `balance`; `historyChanged` → `historyPage`; `vaultLockState` → `lockStatus`; `lockProgress` `done` → `lastLockReport` (the report of the network's last revocation of every lease since its session opened, whatever revoked them: `lock`, the relock timer, `walletlock`, `encryptVault`, `changePassphrase`, `recoverWithMnemonic`, `destroyVault`; `lock` also returns it); `leaseChanged` → `leases`; `dispatchResolved` → `dispatchStatus`/`leases`; `platform` → the domain's queries; `coinJoin` → `coinjoinStatus`; `notice` → `recentNotices` (the last 64 notices). Notices and lock reports have no other home, so `bridge::EventMemory` records them from the mapped event before it is queued: an overflow that drops the event cannot drop them. It keeps a network's report only while that network's session is open (dropped at its `sessionClosed`, the engine's last event for it, and at `sessionOpened`), so it holds at most one report per open network. `newTransactions` is the one exception: a dropped batch loses its popup, and its transactions are in `historyPage`. Payloads are bounded, in the queue and in `EventMemory` alike: `historyChanged` carries at most 256 txids and sends an empty list ("reload the whole history", the engine's own meaning) above that; `newTransactions` carries the first 256 txids and the batch's `count`; a notice's detail is cut to 1024 bytes with a marker saying how many were cut (`dto::cap_text`, which counts bytes as JSON encodes them, escapes included); every other text the engine controls (lease ids, wallet ids, artifacts, identities, drafts) is cut the same way to 128 bytes; a lock report lists at most 16 flows of at most 8 artifacts and at most 16 `walletsWithSecrets`, unresolved outcomes first (`maybeSent`, then `willBeSent`, `sent`, `cancelled`), and counts the rest (`flowsOmitted`, `artifactsOmitted`, `walletsWithSecretsOmitted`; each flow's `outcome` is the strongest of all its artifacts' outcomes, listed or not (E0-04 §8.4: `sent` > `willBeSent` > `maybeSent` > `cancelled`), so only `cancelled` says none of them is pending; `lockStatus` lists every wallet); a lease lists at most 4 budgets (one per purpose) and a sync status 4 phases. A required rule for the report's consumer (since U-07 the renderer's `api/lockReport.ts`, shown by the lock screen, and tested on the fixture's `lock-report-omitted` scenario): a report with `flowsOmitted`, `artifactsOmitted` or `walletsWithSecretsOmitted` above 0 is not complete, so it treats what the report leaves out as unresolved and reconciles through `leases`, `dispatchStatus` and `lockStatus`. Pending is read per artifact, never from a flow's `outcome` (a `sent` registration may hold an identity call still out; scenario `lock-report-pending`). A library call is reported under its label (`send_request`, `accept_request`, `register_name`), which `dispatchStatus` rejects, so a pending one stays unresolved (scenario `lock-report-call`). Omitted items have no ids: omitted artifacts after a listed `sent` or `cancelled` one are settled, but flows are listed by their outcome, so omitted flows are settled only after a listed `cancelled` one, and otherwise stay unresolved. Omitted wallets have no ids either: the consumer reads `lockStatus` after the lock and settles them only when the vault is still locked and its `walletsWithSecrets` holds every listed wallet and at least as many as the report listed and counted; a vault unlocked since, a set that disagrees, or a failed read keeps the report unresolved. The remaining texts have engine-checked bounds (a network name is at most 71 bytes; wallet ids and txids are hex). What is bounded is the DTO that is queued or kept: mapping still reads the whole engine input before it cuts (a lock report's flows and artifacts are sorted, and its wallet ids hex-encoded, before the caps apply; txids are cut first), so that work grows with the engine's report, which the engine bounds by its own flow and wallet counts. So no event encodes to more than 32 KiB (`bridge::MAX_EVENT_BYTES`; the largest is a full lock report, about 29 KB) and most are under 1 KB. Events sent before the page listens are lost; the renderer queries everything at start. The renderer invalidates queries per event (`events.ts`, exhaustive over `AppEvent`). | The engine calls the sink from its own threads and must never wait on the webview, and the process must not grow without bound when the webview stalls (Sol r1 F3). The rate is bounded upstream (the engine debounces `sync`, `balances`, `historyChanged`, `platform` to 4 Hz per domain and `coinJoin` to 1 Hz, trailing edge kept), so the queue fills only when the webview stops reading. Dropping is safe because events are hints and every event's state is queryable (DESIGN-opus §1.5 rule 4); one signal per overflow, not one per drop, keeps the overflow itself bounded. Counting events alone did not bound memory: notice details and lock reports had no size (Sol r2 F3a), and a dropped `done` had no way back (F3b); then `walletsWithSecrets`, escapes and reports of closed networks were still unbounded (Sol r3 F3a). `bridge::tests::every_event_fits_its_byte_bound` builds every event at its largest, with each text encoding to exactly its cap (kept whole: the worst case) and again far over it, and checks the encoded size; `dto::tests::per_variant_caps_count_their_enums` ties the phase and budget caps to their enums; `a_stalled_forwarder_overflows_once_and_stays_bounded`, `oversized_payloads_stay_bounded_and_a_dropped_lock_report_is_kept`, `a_late_overflow_is_reported_by_an_idle_forwarder` and `ipc_tests::the_last_lock_report_is_kept_for_its_network` hold it. |
| D4 engine-side events | Forwarded: `platform`, `leaseChanged`, `lockProgress`, `dispatchResolved`, and the notices `dashPayStartupIncomplete`, `dispatchRecordMissing`, `unscopedDispatch`, `dispatchJournalUnavailable`, `platformTrustMismatch` (E0-10b) that dw-ffi's `forward()` withholds. dw-ffi keeps withholding them. | E0-04 §13, §16.7 and §16.8 and ROADMAP E0-04.P2a keep them engine-side only "until E0-13": the frozen Swift shells cannot carry them, this binding can, and the lease and lock copy (C1–C7) needs them. |
| D5 errors | Every command rejects with one `AppError { code, message, data }`. `code` is a TS union of string literals (`ErrorCode`), one Rust enum per domain: the engine's contract codes (`wallet_not_found`, `vault.locked`, `platform.grant_exceeded`, …), the nested M1–M3 failures with the strings dw-ffi gives them (`send.*`, `labels.*`, `psbt.*`, …), and `app.*` for the binding's own refusals (self-test, handles). "No open network" is the engine's `network_not_open` whether the binding or the engine notices it. Variants dw-ffi folds onto an existing code only because Swift is frozen get their own code here (`send.cancelled`, E0-04.P5). Two domains dw-app adds: `console.*` (dw-ffi's console strings, with `data` `rpc` / `authorize`) and `uri.too_long_for_qr`. `data` is a tagged union of the fields some codes carry (retry wait, shortfalls, budgets, rules…). `message` is diagnostic only. One exception to the shape: an argument that does not deserialize (a missing field, a wrong `kind`, a number over its range) is rejected by Tauri itself with a plain string before the command runs; that is a renderer bug, not a user-facing failure, and `errorMessage` shows it as is. Three record fields carry a failure code the engine stored earlier, as a plain string: `RegistrationFailure.code` (the registration journal), `SyncPassReport.failureCode` and `MixedCoinsSweepResult.failureCode`. They are the engine's own strings (`EngineError::code`, which includes bare domains such as `signer`), not all of them in `ErrorCode`, so they stay `string`; the renderer narrows them against `ERROR_CODES`. Each engine error type maps through an exhaustive `match`. | The UI picks copy by `code`, so a `switch` over it is checked by tsc and a misspelt code does not compile. One shape for every command keeps error handling in one place. |
| D6 numbers and bytes | Duffs, heights, counts and UNIX times are JSON numbers (all < 2^53: 21×10^14 duffs). Platform credits, credit budgets and credit shortfalls are decimal strings (`dto::credits`). Bytes are base64 strings (`dto::base64`), PSBTs base64, txids and wallet ids lower-case hex, identities Base58. Keys the engine already gives as hex (`IdentityKeyInfo.publicKey`) stay hex. Lease ids: `beginFlow` and flow reports carry the full `lease-<32 hex>`; `Lease.id` in `leases` and `leaseChanged` is its first 8 hex digits (the engine's display id), so the renderer matches a flow's lease by that prefix. | A credit amount can exceed 2^53; JSON numbers would round it silently. |
| D7 one active session | The window shows one network. `openNetwork(network, settings)` (`null`: the launch network, the launch flags) makes it the active one, closing the one before it and dropping its handles; every session command acts on the active one; `closeNetwork` closes it. A switch holds the session slot while the old network closes and the new one opens, so session commands issued meanwhile wait for it rather than reach a half-closed session. | Data is per network (QT-002) and the shell shows one; the renderer never names a network per call, so it cannot act on the wrong one. |
| D8 handles | Engine objects that live across calls (`TxDraft`, `PreparedTx`) cross as `u64` handles (`state::SendHandles`), capped at 64 per kind (a prepare reserves its prepared slot under the lock before it awaits signing and counts against the cap until it fills or drops it, so a full table fails with `app.too_many_handles` before the grant is redeemed; a failed or cancelled prepare, closing the draft and switching network release the reservation), never reused within a process. One lock covers both kinds and an epoch that `openNetwork` / `closeNetwork` advance when they drop every handle: a draft is stored only in the epoch of the session that made it, and a prepared transaction only while its draft is open, so a prepare that finishes after `closeDraft` or a network switch is dropped (its inputs are released) and the call fails with `app.unknown_handle`. `draftPrepare` returns the prepared handle with its summary. A prepared handle belongs to its draft (`draftBroadcast` / `draftAbandon` refuse another draft's with `invalid_argument`). `draftBroadcast` drops it when the network accepted the transaction and when a first broadcast released it (`send.no_peers`, `send.broadcast_rejected`, `send.prepared_tx_spent`, `send.cancelled`: prepare again); it stays after `send.broadcast_unknown` and failures before dispatch, so the call can be repeated. `draftAbandon` releases one prepared transaction and leaves the draft editable, as the engine does; `closeDraft` drops the draft, its prepared handles and its prepares' reservations. It only refuses later calls: a `draftBroadcast` already running holds its own references, finishes and reports its outcome, so the transaction may still be sent (a network switch waits for it: the broadcast holds the session open). The send screen (U-03) closes drafts through `api/send.ts` `closeSendDraft`, which gives DEC-67's line, "Lock stops new signatures; a transaction already signed may still be sent", to show when the screen's broadcast of that draft is running (Sol r1 F4: documented, not serialized). The signed bytes (`PreparedTx::raw`) never cross: they leave the process only through the dispatch fence's hand-off (E0-04 §2). | They hold state the renderer cannot hold (a draft's recipients, a signed transaction); a leaking renderer gets `app.too_many_handles` instead of growing the process, and no handle outlives its draft or session. |
| D9 session settings | `SessionSettings` carries E0-02's `caCertPath` and `initialProtocolVersion` (plus DAPI addresses, quorum URL, SPV peers, no-Platform); the launch flags `--ca-cert`, `--protocol-version`, `--quorum-url`, `--dapi`, `--spv-peer`, `--no-platform` fill what the renderer leaves out. | E0-02 left them out of dw-ffi so Swift stayed unchanged. A devnet's settings come from a file dialog in the renderer (U-01). The CA and quorum URL are trust settings: the engine requires https for the quorum service on mainnet and testnet, and a CA only adds roots for DAPI TLS (Platform data stays proof-verified). On mainnet and testnet, `openNetwork` refuses DAPI addresses, a quorum URL, SPV peers and a CA certificate from the renderer (`invalid_argument`): there they come from launch flags only, so script in the window cannot repoint a public network's trust. U-01 should keep the devnet ones behind an explicit network-settings flow. |
| D10 commands | Every command is `async` (Tauri runs sync commands on the main thread) and thin: parse arguments, call the facade, map to a DTO. Secrets the renderer sends are wrapped in `Zeroizing` when the command receives them, before any early return. Copies outside the binding's reach are an accepted risk, as in G-01 H-01: the renderer's own strings, and in the Rust process Tauri's request body and the `serde_json::Value` it parses arguments from, which Tauri drops without zeroing (bearer invitation links, mnemonics, passphrases, console lines alike). dw-ffi took them as bytes; a raw-body command would avoid the `Value` copy but not the webview's, so E0-13 does not. DTOs are dw-app's own camelCase mirrors; every `From` destructures exhaustively and every `match` names every variant, so an engine change breaks the build instead of dropping a field. The DashPay records' snake_case serde (their persistence form) is not reused. | No engine call may block the window; one shape rule for every record. |
| D11 security | G-02's posture is kept: CSP, frozen prototype, no global Tauri, the navigation block, text-only rendering. Commands are granted per domain in `capabilities/<domain>.json`, to the main window only; `build.rs` derives the permission set from those files, and `api::tests::every_command_is_granted_in_its_domain_file` pins grants to declared commands. `probe_unlisted` is registered and never granted (U6). "Require authentication for every payment" (DESIGN-opus §1.8, default on) is enforced here, not in the renderer: `NetworkSession::payment_authentication` stores it in the network's app.sqlite under the vault's id (`Vault::vault_id`, random per vault file), so it belongs to that vault: a vault created after `destroyVault`, or by a recovery, has a new id and starts on; while it is on, `authorize` / `authorizeSet` refuse `spend` and `platformOp` on an unlocked encrypted vault with the `unencrypted` credential (`vault.credential_required`; locked, the vault's own `vault.locked` comes first), so the console's `sendtoaddress` after `walletpassphrase` also needs a credential per payment. Changing it either way takes a `changeCredential` grant, so the passphrase; on a vault without one it cannot be changed (`vault.not_encrypted`): there is nothing to ask for, and a value stored then would carry over, unasked, to the vault once encrypted. Reading the setting and issuing the grant are one step (`state::PaymentPolicy`): the setter holds one policy mutex while it advances a generation and then writes the setting, and `authorize` reads the generation and the setting under that mutex, so no read pairs the new value with the old generation. Once the grants exist `authorize` compares the generation again: if it moved, or the vault was replaced, the stricter rule decides and a refusal revokes what was issued. A write that is readable has advanced the generation first, so a grant issued once "on" is readable was not judged under "off". Grants issued and leases started before a change keep working until used or expired (grants live 120 s). `signMessage` and the other purposes keep the vault's rules. | A compromised renderer could otherwise skip its own prompt and take a payment grant (Sol r1 F1), or keep "off" across a new vault or win a race against turning it on (Sol r2 F1), including the window between the write and the generation's advance when it came after the write (Sol r3 F1b). `ipc_tests::a_grant_issued_once_the_strict_value_is_readable_is_refused` stops the setter right after its write; `authorize_waits_for_a_policy_write_in_progress` stops it between the advance and the write. Their test seams (`state::Seam`) time out rather than hang, and let a paused call go on when a test fails. Every new command is in the allowlist explicitly, and a command cannot be callable without a grant or granted without existing. |
| D12 helper commands | Commands that reach no facade method are the host helpers dw-ffi also exposes: `parsePaymentUri`, `buildPaymentUri`, `classifyAddress`, `qrMatrix` (dw-uri), `verifyMessage` (dw-message), `formatAmount`, `parseAmount`, `unitName` (dw-units: dash-qt's amount rounding and parsing, so the renderer never re-implements them), `consoleCommands`, `consoleRedact` (dw-console; `consoleExecute` runs on `NetworkSession::run_on_engine`), `coinjoinLimits`, `closeDraft`, and the app's own (`launchInfo`, `activeNetwork`, measurement and self-test). dw-ffi's `network_stats` is not bound: it only reshapes `nodeInfo`, which carries the masternode counts and the best ChainLock (its other fields are `null` in SPV). dw-desktop (autostart, notifications, QR capture and `decode_qr_codes`, log export, URI scheme registration) is OS integration, not a facade; U-01 binds what Tauri's own plugins do not cover. dw-ffi's `core_version` is the app's version, which Tauri's `getVersion` gives. | The coverage test is about facades; helpers are bound where a screen needs them, with no logic beyond the helper crate's. |
| D13 outcomes as data | `verifyMessage` returns `{ outcome, text }` (dash-qt's status line per outcome) and `parsePaymentUri` returns `{ kind: "accepted", uri }` or `{ kind: "rejected", reason }`. dw-ffi's `message.*` and `uri.*` failure codes are therefore not in `ErrorCode`, except `uri.too_long_for_qr` (`qrMatrix`, dash-qt's "Resulting URI too long"). dw-ffi's per-domain spellings of engine codes (`wallet.vault_locked`, `sync.spv_not_running`, `history.tx_not_found`, `psbt.vault_locked`, …) are the engine's own codes here (`vault.locked`, `spv_not_running`, `tx_not_found`; `signPsbt`'s locked vault or bad grant, which the engine reports as `SendFailure`, is `send.vault_locked` / `send.grant_invalid`); signing with a watch-only wallet fails with the engine's own code (the vault's grant or signer codes), not dw-ffi's `message.watch_only`. `generateMnemonic`'s unsupported word count is `invalid_argument`. | Rejecting a pasted URI or a wrong signature is an expected answer the screen renders inline, not a failure; one spelling per failure keeps the TS `switch` short. |
| D14 type names | ts-rs writes one file per TypeScript name, so two Rust records of one name would overwrite each other. `write_bindings` walks every named type it exports (dependencies included) and fails when two differ in declaration for one file (`codegen::tests::a_type_name_clash_is_refused`). | Six slices added DTOs in parallel; a silent overwrite would type one command with another's record. |
| D15 tests | `ipc_tests` builds the app as `run` does, on Tauri's mock runtime with a real engine in a private data root (offline endpoints, in-memory OS store, test KDF), and calls one command per facade through the webview's IPC handler with camelCase JSON: the free functions, `Engine`, `Vault`, `NetworkSession` (and the console), `TxDraft`, `PreparedTx` and `DashPay`, plus the binding's refusals. `apps/desktop/src/api/commands.test.ts` (vitest) calls the generated wrappers through `mockIPC` against a fixture typed by `CommandArgs` / `CommandResults`, so tsc also checks it, and checks that the wrappers and `COMMANDS` agree. | The Rust test proves the wire format against the engine; the vitest proves the generated TS sends what the Rust side reads. |
| D16 self-test passphrase file | `selftest_unlock` reads `--selftest-passphrase-file` through `dw_fs::open_owner_only`: on Unix the file must be a regular file the user owns, with no group or other permission bits, not reached through a symlink (`O_NOFOLLOW`, then `fstat` on the descriptor). Anything else, and a file that cannot be read, fails as `app.selftest_passphrase_file` with the reason, and the self-test's final report carries the code (`error: "<code>: <message>"`), which `selftest-judge.jq` prints. **Windows: no check in Rust.** `tauri-selftest.yml` gives the file an ACL of one entry (`icacls /inheritance:r /grant:r <job user>:F`) before writing the passphrase; on Unix it creates the file under `umask 077` and `chmod 600`. | A passphrase another local user can read unlocks the vault. Reading Windows ACLs from Rust needs a `windows-sys` security-descriptor walk for a CI-only file; the runner's job user and its temp directory are the job's own, and the workflow sets the ACL itself. |
