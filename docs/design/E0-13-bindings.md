# E0-13: the facades bound for Tauri

ROADMAP E0-13 for the Tauri stack (G-04, DEC-190, ADR 0003): `dw-app` commands, generated
TypeScript types and the event bridge. UniFFI `dw-ffi` stays frozen and gains nothing; Governance
and Masternodes are bound later (MG). Code: `rust/crates/dw-app/src/{ipc,api,dto,error,bridge,codegen,coverage}.rs`;
generated files: `apps/desktop/src/api/generated/`; coverage table: [E0-13-facade-coverage.md](E0-13-facade-coverage.md).

| # | Decision | Why |
|---|---|---|
| D1 types | ts-rs 12 writes one `.ts` per record. A command manifest (`ipc::commands!`) declares each command once and also emits its spec (arguments, result, docs, facade claims); `codegen` turns the specs into `generated/commands.ts`: a typed wrapper per command (camelCase name and arguments, trailing nullable arguments optional), `CommandArgs` / `CommandResults` maps, `COMMANDS`, `ERROR_CODES`, `ENGINE_EVENT`. The generated files are committed; `codegen::tests::bindings_are_current` fails when they are stale, and CI regenerates them (`DW_UPDATE_BINDINGS=1`) and runs `git diff --exit-code`. | One source per command, so a Rust signature change cannot leave the TS side behind. tauri-specta is still 2.0.0-rc.25 on a pinned rc of specta; ts-rs is what G-01 chose and G-02 used. Committed files let the renderer build without Rust and make every binding change visible in review. |
| D2 coverage | Every `pub fn` of `Engine`, `NetworkSession`, `DashPay`, `TxDraft`, `PreparedTx` and `Vault`, read from the dw-engine and dw-vault sources, plus the free functions hosts call (`coverage::FREE`), is either claimed by a command's `#[facade("Type::method")]` or listed in its domain's `EXCLUDED` with a reason, never both. Reasons are `internal: …` (engine plumbing no host calls: signers, paths, closures the binding wraps) or `deferred (MG): …`. `coverage::tests::facades_are_covered` fails on an unclaimed, doubly-listed or unknown method; the table is generated and checked like the bindings. | A facade method added later fails the test until someone decides to bind or exclude it; the reasons are reviewable in one table. |
| D3 events | One Tauri event, `engine://event`, with a typed payload `AppEvent` (a one-to-one mirror of `EngineEvent`). `TauriSink::emit` only sends into an unbounded channel; a dedicated thread maps each event to its DTO and emits it. Order: FIFO across all kinds (one channel, one consumer, one event name). No event is dropped. Payloads are bounded: `historyChanged` carries at most 256 txids and sends an empty list ("reload the whole history", the engine's own meaning) above that; `newTransactions` carries the first 256 txids and the batch's `count`. Events sent before the page listens are lost; the renderer queries everything at start. The renderer invalidates queries per event (`events.ts`, exhaustive over `AppEvent`). | The engine calls the sink from its own threads and must never wait on the webview. Dropping is wrong for one-shot events (`lockProgress` `done`, `dispatchResolved`); the rate is already bounded upstream (the engine debounces `sync`, `balances`, `historyChanged`, `platform` to 4 Hz per domain and `coinJoin` to 1 Hz, trailing edge kept), so the queue stays short. Events are hints; data is re-queried (DESIGN-opus §1.5 rule 4). |
| D4 engine-side events | Forwarded: `platform`, `leaseChanged`, `lockProgress`, `dispatchResolved`, and the notices `dashPayStartupIncomplete`, `dispatchRecordMissing`, `unscopedDispatch`, `dispatchJournalUnavailable` that dw-ffi's `forward()` withholds. dw-ffi keeps withholding them. | E0-04 §13, §16.7 and §16.8 and ROADMAP E0-04.P2a keep them engine-side only "until E0-13": the frozen Swift shells cannot carry them, this binding can, and the lease and lock copy (C1–C7) needs them. |
| D5 errors | Every command rejects with one `AppError { code, message, data }`. `code` is a TS union of string literals (`ErrorCode`), one Rust enum per domain: the engine's contract codes (`wallet_not_found`, `vault.locked`, `platform.grant_exceeded`, …), the nested M1–M3 failures with the strings dw-ffi gives them (`send.*`, `labels.*`, `psbt.*`, …), and `app.*` for the binding's own refusals. Variants dw-ffi folds onto an existing code only because Swift is frozen get their own code here (`send.cancelled`, E0-04.P5). Two domains dw-app adds: `console.*` (dw-ffi's console strings, with `data` `rpc` / `authorize`) and `uri.too_long_for_qr`. `data` is a tagged union of the fields some codes carry (retry wait, shortfalls, budgets, rules…). `message` is diagnostic only. Each engine error type maps through an exhaustive `match`. | The UI picks copy by `code`, so a `switch` over it is checked by tsc and a misspelt code does not compile. One shape for every command keeps error handling in one place. |
| D6 numbers and bytes | Duffs, heights, counts and UNIX times are JSON numbers (all < 2^53: 21×10^14 duffs). Platform credits, credit budgets and credit shortfalls are decimal strings (`dto::credits`). Bytes are base64 strings (`dto::base64`), PSBTs base64, txids and wallet ids lower-case hex, identities Base58. | A credit amount can exceed 2^53; JSON numbers would round it silently. |
| D7 one active session | The window shows one network. `openNetwork(network?, settings?)` makes it the active one, closing the one before it and dropping its handles; every session command acts on the active one; `closeNetwork` closes it. | Data is per network (QT-002) and the shell shows one; the renderer never names a network per call, so it cannot act on the wrong one. |
| D8 handles | Engine objects that live across calls (`TxDraft`, `PreparedTx`) cross as `u64` handles in a capped table (64 per kind), never reused within a process, cleared when the session closes. `draftPrepare` returns the prepared handle with its summary. A prepared handle belongs to its draft (`draftBroadcast` / `draftAbandon` refuse another draft's with `invalid_argument`); a broadcast the network accepted drops it, `send.broadcast_unknown` keeps it so the call can be repeated. `draftAbandon` releases one prepared transaction and leaves the draft editable, as the engine does; `closeDraft` drops the draft and its prepared handles. | They hold state the renderer cannot hold (a draft's recipients, a signed transaction); a leaking renderer gets `app.too_many_handles` instead of growing the process. |
| D9 session settings | `SessionSettings` carries E0-02's `caCertPath` and `initialProtocolVersion` (plus DAPI addresses, quorum URL, SPV peers, no-Platform); the launch flags `--ca-cert`, `--protocol-version`, `--quorum-url`, `--dapi`, `--spv-peer`, `--no-platform` fill what the renderer leaves out. | E0-02 left them out of dw-ffi so Swift stayed unchanged. A devnet's settings come from a file dialog in the renderer (U-01). The CA and quorum URL are trust settings: the engine requires https for the quorum service on mainnet and testnet, and a CA only adds roots for DAPI TLS (Platform data stays proof-verified). U-01 should keep them behind an explicit network-settings flow. |
| D10 commands | Every command is `async` (Tauri runs sync commands on the main thread) and thin: parse arguments, call the facade, map to a DTO. Secrets the renderer sends are wrapped in `Zeroizing` on receipt; the renderer's own copies cannot be zeroed (G-01 H-01). DTOs are dw-app's own camelCase mirrors; every `From` destructures exhaustively and every `match` names every variant, so an engine change breaks the build instead of dropping a field. The DashPay records' snake_case serde (their persistence form) is not reused. | No engine call may block the window; one shape rule for every record. |
| D11 security | G-02's posture is kept: CSP, frozen prototype, no global Tauri, the navigation block, text-only rendering. Commands are granted per domain in `capabilities/<domain>.json`, to the main window only; `build.rs` derives the permission set from those files, and `api::tests::every_command_is_granted_in_its_domain_file` pins grants to declared commands. `probe_unlisted` is registered and never granted (U6). | Every new command is in the allowlist explicitly, and a command cannot be callable without a grant or granted without existing. |
| D12 helper commands | Commands that reach no facade method are the host helpers dw-ffi also exposes: `parsePaymentUri`, `buildPaymentUri`, `classifyAddress`, `qrMatrix` (dw-uri), `verifyMessage` (dw-message), `consoleCommands`, `consoleRedact` (dw-console; `consoleExecute` runs on `NetworkSession::run_on_engine`), `coinjoinLimits`, `closeDraft`, and the app's own (`launchInfo`, `activeNetwork`, measurement and self-test). dw-ffi's `network_stats` is not bound: it only reshapes `nodeInfo`, which carries the masternode counts and the best ChainLock (its other fields are `null` in SPV). dw-desktop (autostart, notifications, QR capture, log export, URI scheme registration) is OS integration, not a facade; U-01 binds what Tauri's own plugins do not cover. | The coverage test is about facades; helpers are bound where a screen needs them, with no logic beyond the helper crate's. |
| D13 outcomes as data | `verifyMessage` returns `{ outcome, text }` (dash-qt's status line per outcome) and `parsePaymentUri` returns `{ kind: "accepted", uri }` or `{ kind: "rejected", reason }`. dw-ffi's `message.*` and `uri.*` failure codes are therefore not in `ErrorCode`, except `uri.too_long_for_qr` (`qrMatrix`, dash-qt's "Resulting URI too long"). dw-ffi's per-domain spellings of engine codes (`wallet.vault_locked`, `sync.spv_not_running`, `history.tx_not_found`, …) are the engine's own codes here (`vault.locked`, `spv_not_running`, `tx_not_found`); signing with a watch-only wallet fails with the engine's own code (the vault's grant or signer codes), not dw-ffi's `message.watch_only`. `generateMnemonic`'s unsupported word count is `invalid_argument`. | Rejecting a pasted URI or a wrong signature is an expected answer the screen renders inline, not a failure; one spelling per failure keeps the TS `switch` short. |
| D14 type names | ts-rs writes one file per TypeScript name, so two Rust records of one name would overwrite each other. `write_bindings` walks every named type it exports (dependencies included) and fails when two differ in declaration for one file (`codegen::tests::a_type_name_clash_is_refused`). | Six slices added DTOs in parallel; a silent overwrite would type one command with another's record. |
| D15 tests | `ipc_tests` builds the app as `run` does, on Tauri's mock runtime with a real engine in a private data root (offline endpoints, in-memory OS store, test KDF), and calls one command per facade through the webview's IPC handler with camelCase JSON: the free functions, `Engine`, `Vault`, `NetworkSession` (and the console), `TxDraft`, `PreparedTx` and `DashPay`, plus the binding's refusals. `apps/desktop/src/api/commands.test.ts` (vitest) calls the generated wrappers through `mockIPC` against a fixture typed by `CommandArgs` / `CommandResults`, so tsc also checks it, and checks that the wrappers and `COMMANDS` agree. | The Rust test proves the wire format against the engine; the vitest proves the generated TS sends what the Rust side reads. |
