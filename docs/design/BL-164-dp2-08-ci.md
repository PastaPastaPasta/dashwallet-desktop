# BL-164: DP2-08's two CI regressions on main (Windows engine, Tauri smoke)

Backlog row BL-164. Main CI on d0fef6b4 (run 38831288544, the DP2-08 merge) failed two jobs DP2-08 had not run:
the Windows engine tests and the Tauri E2E smoke. Both are fixed on `dw/bl-164-dp2-08-ci` from main 913893dd. Neither
was a product delay: the Windows failure was a test that assumed Linux, and the smoke waited on an element WebDriver
can never call displayed. The Swift T0 failure in the same run is unrelated (D3).

| Part | Where |
|---|---|
| `read_image` checks the path before it opens it | `rust/crates/dw-desktop/src/screen.rs` (`read_image`, `test_IOS_043_…`) |
| The smoke waits for the link's block and pins the unreachable-Platform outcome | `apps/desktop/e2e-tauri/smoke.ts` (second launch, `dashpay:`), `driver.ts` (`waitFor` note) |

## Decisions

**D1. A directory is `ImageUnreadable` on every OS: `read_image` stats the path before it opens it.** On Windows
`File::open` on a directory fails (a directory opens only with `FILE_FLAG_BACKUP_SEMANTICS`), so the old code returned
`OsError` there and `ImageUnreadable` on Linux and macOS; `test_IOS_043_captures_are_regular_files_of_at_most_32_mib`
asserted the Linux answer. Accepting either code in the test would have kept two error codes for one refusal, and the
renderer maps the code (a refusal versus a failure). So `read_image` now checks `fs::metadata(path)` first (a regular
file of at most 32 MiB, else `ImageUnreadable`), opens it, and checks the open file's metadata again, because the path
may have been replaced in between. A missing path is still `OsError`. The test is unchanged apart from a comment.
Evidence: Linux `cargo test -p dw-desktop --lib` 30/30; the `x86_64-pc-windows-gnu` test binary under Wine (Docker,
the recipe in the box notes) 17/17; with the pre-open check removed the Wine run fails at the directory assertion,
reproducing CI. `cargo clippy -p dw-desktop --all-targets -D warnings` is clean for Linux and the Windows target. CI
runs MSVC; the code has no target-env cfg.

**D2. The forwarded link never waited 120 s: the smoke waited on a line WebKitWebDriver cannot call displayed.** The
smoke (`smoke.ts`) waited for `add-contact-username` after a second launch with `dashpay://user?…&username=bob` and
timed out after its full 120 s; the failure screenshot already showed "@bob · Could not reach Dash Platform · Try
again". Reproduced locally with `scripts/e2e-tauri.sh` on 913893dd (agentbox, X display, load ~50). An instrumented copy
of the smoke polled the DOM and timed every WebDriver call after the second launch:

| After the second launch | DOM | `/displayed` of `add-contact-username` | WebDriver call times |
|---|---|---|---|
| 219 ms (the launch took 219 ms) | Contacts, link block, "@bob", "Checking @bob on the Dash network…" | false | 13–47 ms |
| 1.3 s, and every second to 85 s | "@bob", "Could not reach Dash Platform. Try again" | false | 6–170 ms |

So the card shows at once with "@bob" while it checks, and regtest's absent Platform resolves in about a second; no
call blocks and the UI thread keeps running. The username line is `<p class="contact-row-username">`, which has
`overflow: hidden` (the row's ellipsis). Toggling its inline style: `overflow: visible` makes it displayed;
`text-overflow`, `white-space`, `display` and `line-height` do not. Its block, the error line and Close read displayed.
WebKit's atom (`Source/WebKit/UIProcess/Automation/atoms/utils.js`, `isShown`) explains it: an element whose cascaded
`overflow` is `hidden` is "hidden by overflow" when every child is, and a text node always counts as hidden there (a
FIXME notes the check is incomplete). Any text-only element with `overflow: hidden` is therefore never displayed to
WebKitWebDriver, however it looks. The app's styling is right, so the fix is in the smoke: it waits for the link's
block (`add-contact-link`), reads the username in it with `innerText` through a script (as the Add Contact GL does),
then waits, with half the budget, for the link check's error and checks it says "Could not reach Dash Platform". The
step line records both times. `driver.ts`'s `waitFor` documents the trap. No other `waitFor`/`press`/`fill` target in
`e2e-tauri/` has a class with `overflow: hidden` (a scan of the 114 test ids against `app.css`). Result: the smoke
passes 11/11, "@bob after 581 ms, Platform unreachable after 1382 ms". DP2-08's gate never ran the smoke, which is why
main CI found this first.

**D3. Swift T0 `SPVCoordinatorTests.doneOnlyAfterThePeakDelay` is a different timing pattern; noted, not fixed.**
It failed after 12.130 s at `LifecycleTests.swift:259` (`await eventually { sync.status?.isDone == true }`). It passed
on 8276bf62 and the DP2-08 merge changed no Swift. `eventually` is 400 polls of 5 ms (about 2 s), so its 12 s means each
5 ms sleep took about 30 ms: the runner was starved. The test waits for any sleeper on its `ManualClock`, advances
3000 ms, sleeps 20 ms of real time, then advances 250 ms to reach `peakDelay` (3250 ms). `SPVCoordinator.apply` computes
the peak task's `delay` when it runs, but the task registers its sleep later, at the clock's `current + delay`, and every
later `apply` replaces the `peak` task. Unlike its neighbour test, this one does not `settle()` the refresh the SPV-start
event triggers. On a starved runner that refresh can replace the sleeper the test saw with one that registers after the
second advance, at a deadline past 3250 ms (3500 ms if it applied between the advances, 6500 ms if before both), so
nothing wakes and `isDone` never turns true. This is a real-time race in a test, the
same family as D2 only in that load exposed it; it is not a WebDriver oracle, and in the app (a real clock) the late
registration only makes the peak a little longer. A fix (settle the start refresh first; wait for the sleeper after it,
or sleep until a deadline instead of for a delay) needs a Swift run to prove; agentbox has no Swift toolchain, so it is
left for a Swift task, not fixed here. Rerun alone before blaming a branch.
