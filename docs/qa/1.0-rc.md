# 1.0 release candidate: the QA run sheet

The run sheet for the Dash Wallet Desktop 1.0 release candidate. The candidate is tagged on 2026-11-30, and 1.0
follows on 2026-12-02 ([`PLAN-1.0.md`](../PLAN-1.0.md)). Every user story in [`parity.md`](../parity.md) is crossed
with macOS, Windows and Linux here, and each cell says who or what runs it. The release notes'
"How 1.0 was tested" ([`1.0.0-notes.md`](../release/1.0.0-notes.md)) is filled from this sheet.

This sheet does not repeat the by-hand steps. They are in [`H-08-macos-windows.md`](H-08-macos-windows.md) (install,
upgrade, uninstall, DashPay, VoiceOver and Narrator on macOS and Windows) and
[`screen-reader-linux.md`](screen-reader-linux.md) (the AT-SPI walk). A cell that names an H-08 section means
"run that section and record its result here as well".

## 1. What is tested, and how

### The build under test

The files of the Release run on the tag `v1.0.0-rc.N`, downloaded from its GitHub release (a prerelease) and checked
with `SHA256SUMS` and `gh attestation verify` first (H-08 §1, [`verifying.md`](../release/verifying.md)):

| OS | File | State |
|---|---|---|
| macOS (Apple silicon and Intel) | `dash-wallet-1.0.0-rc.N-macos-universal.dmg` | ad-hoc signed, not notarized: Gatekeeper blocks the first launch |
| Windows (x64) | `dash-wallet-1.0.0-rc.N-windows-x64-setup.exe` | unsigned NSIS installer, per user: SmartScreen blocks the first run |
| Linux (x86_64) | `dash-wallet-1.0.0-rc.N-linux-x86_64.AppImage`, `…-linux-amd64.deb`, `…-linux-x86_64.flatpak` | unsigned; the Flatpak repackages the .deb's binary |
| all | `SHA256SUMS`, `dash-wallet-1.0.0-rc.N-sbom-rust.cdx.json`, `dash-wallet-1.0.0-rc.N-sbom-npm.cdx.json` | attested by the Release workflow |

A candidate has no `latest.json` and no macOS update archive: it is never offered as an update. Settings ▸ About
shows the tag's version without its `v` (`1.0.0-rc.N`), and Tools ▸ Information shows the test-build warning once no higher-priority warning is up (the final tag must not). Write the candidate's
tag and commit SHA at the top of the results before anything else.

### Networks

- **Testnet** by default, for every row. Agents fund wallets with the `dash-faucet` skill; a person uses the testnet
  faucet in a browser.
- **Regtest** for what testnet cannot give: masternode collateral (1,000 tDASH, or 4,000 for an evonode, is more than
  the faucet gives), governance with our own masternodes, and stuck-transaction states. These run as the regtest
  suites in `regtest/functional/` and `regtest/harness/tests/`, and the `e2e-tauri` regtest drivers.
- **Mainnet** only in the 💰 rows (the H-07 canary): a wallet made for the canary, at most 0.5 DASH in all.

Some flows are off on mainnet in 1.0 and are tested on test networks only. Their rows say **test networks only (off on
mainnet)**: testnet, or regtest where the row says so. In the code at the time of writing these are:

|---|---|
| Masternode and evonode registration sends (ProRegTx) | `masternodes/registration.ts` `registrationSends`; engine `masternodes/protx.rs` `require_protx_sending` |
| Changing a masternode's voting, payout or operator key (ProUpRegTx) | `masternodes/changeKeys.ts` `registrarUpdateSends`; engine `require_protx_sending` |
| Shared-masternode registration sends (start, join, lock, approve, sign, send). Reward change, key rotation, dissolve, and creating, exporting or sending a standby have no desktop binding yet (engine only); importing and saving a received standby is in the app. Way-out steps (discard, abandon) still run | `masternodes/shared.ts` `sharedSendsOn`; `dw-app` `api/masternodes.rs` `shared_sends_allowed` |
| Paying a contact from the Platform balance | `screens/pay/fromBalance.ts` `liveSources`; engine `platform/contact_payout.rs` |
| Paying several recipients in one payment | `screens/pay/model.ts` `multiRecipientPay` |

Three sources are not offered on any network in this build: a username registration paid from the Platform balance (`dashpay/payWith.ts` `LIVE_SOURCES` holds Core only; the engine's start returns `platform.feature_off`), paying a contact from the Shielded balance (`liveSources`
holds Core and Platform only; the engine refuses `shielded_contact_payment`), and registering a username or topping
up from the Shielded balance (`dashpay/topupSource.ts` lists Shielded and does not offer it; the engine's
`shielded_registration` has no funding step yet). Their rows say so. Exchange rates and fiat amounts are the other way
round: the app fetches rates on mainnet only, so fiat rows are checked by CI on fixture data.

### Evidence

- Testnet, regtest or fixture data only. Never a recovery phrase, a passphrase, a private key, a backup file or an
  invitation link in a screenshot, a recording, an issue or this sheet. A row on a phrase or passphrase screen is
  reported in words only.
- Never use a real mainnet phrase in a fixture or in evidence. In the 💰 rows, record results in words and in
  screenshots with every address and txid redacted; usernames and display names may stay, they are public.
- Screenshots in light **and** dark. Open every image before uploading it and crop anything private (a user name in a
  path, a Keychain or Credential Manager prompt, another app).
- Images go to a `pr-artifacts/…` branch, never to `main`, and are linked by raw URLs pinned to that branch's commit
  SHA. Caption each one with the row ID, the state and the build (`v1.0.0-rc.N`, its short SHA).
- The agent runs (`agentic-qa`) publish their report with screenshots and recordings as that skill describes, and link
  it from the results here.

### Recording a result

Each table has a **Result** column. Leave it blank until the row has run, then write one of:

- `pass` (with the runner, the OS and the date when the row has more than one runner);
- `fail #<issue>`, with the issue filed first (OS, build, steps, redacted evidence);
- `blocked: <reason>`, when the row could not run (for example "Shielded not active on testnet", "the testnet
  faucet is down");
- `not exercised` (per OS), only when `CI` or `launch` alone covers that OS's cell, or where a row names it as its
  exception (IOS-077 without its own invitation link). A missing prerequisite elsewhere is `blocked` (for example
  SW-1's "no Swift-app data");
- `n/a`, only where the row or its section already says why.

A row with several runners is `pass` only when each of them passed; write the failing runner in the cell otherwise
(for example `fail #812 (pasta-win)`). A blocker or critical failure holds the candidate (CHECKLIST §4). The run is
complete when no Result is blank in the 🖥 rows and the minimal bar, and every other row is `pass`, `fail #…` with a
triage decision, `blocked` with a reason, `n/a` where the row or its section gives the reason, or `not exercised` as defined above. A cell on any OS, Linux included, that only `CI` or `launch` covers is
recorded as `not exercised` on that OS, never as `pass`; CHECKLIST §4 asks for interactive QA of every story on all three OSes, so
T-2 passes only when those cells are run or the release owner writes the exception down (who, when, which rows).

**Flags.** 🖥: the row needs Pasta's hardware (a real Mac or Windows PC, or a VM on it). 💰: the row needs mainnet
funds. Both are collected in section 7.

**What macOS and Windows get.** Agents cannot drive a macOS or Windows GUI here (hosted runners return black
screenshots), so the Release workflow only launch-checks those two. A row without 🖥 is covered on macOS and Windows
by `CI` and `launch` alone: the same renderer and engine as Linux, without anyone using it on that OS. The rows with 🖥
are the ones where the OS changes what the user gets (installer, first launch, secret store, menus and tray, file
dialogs, screen readers, upgrade in place) plus the DashPay journeys H-08 runs across the two OSes. The release
notes must say which stories ran on a real Mac and a real Windows PC and which ran on Linux only.
