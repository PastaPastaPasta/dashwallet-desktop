# Dash Android wallet: user-facing feature inventory (AND-001 to AND-150)

This is research input for "DashPay on desktop". It lists every user-facing feature of the Dash Android wallet, maps each one to the iOS checklist (IOS-001 to IOS-123 in `docs/parity.md`), and calls out what Android has that iOS does not, and the reverse.

- **Source:** `/Users/pasta/workspace/dashwallet-desktop-deps/dash-wallet-android` (dashpay/dash-wallet `master`, HEAD `a8de1f0794` dated 2026-10-07, "fix(dashpay): share invite links the iOS wallet can open (#1586)"). The checkout is shallow, with one commit. It was read only; nothing was changed.
- **iOS side:** `docs/parity.md` IOS rows, `docs/research/03-ios-features.md`, and spot checks in `/Users/pasta/workspace/dashwallet-ios`.
- **Method:** I walked the manifest, all 13 navigation graphs, every Activity, Fragment, Compose screen and dialog, the menus, the English string resources, and the service and worker code behind each screen.

**Columns:** ID · Feature · What it does · Entry point · Source · External dependencies · iOS match.

**iOS match legend**
- `IOS-xxx` means the same feature exists.
- `≈IOS-xxx` means a similar feature with a different flow.
- `—` means iOS has no equivalent.
- `(iOS removed)` means iOS dropped it on purpose. See `docs/research/03-ios-features.md` §1.22.

## 0. App shape, gates and build facts

These facts change how most features are scoped.

| Topic | Android behaviour | Where | Contrast with iOS |
|---|---|---|---|
| Network | Fixed at build time by product flavor: `prod` (mainnet), `_testNet3` / `staging` (testnet), `devnet` (Ouzo). Each flavor is a separate APK. There is **no runtime network switch**. | `W/Constants.java` (`switch (BuildConfig.FLAVOR)`), `wallet/{prod,testNet3,staging,devnet}/` | iOS switches network at runtime and has a Devnet settings screen (IOS-106). |
| Feature flags | `SUPPORTS_PLATFORM` (true except on 32-bit ABIs), `SUPPORTS_INVITES` (true), `SUPPORTS_TXMETADATA` (true), `SUPPORTS_CONNECT` (**false on prod**, true on testnet/devnet), `SUPPORTS_MAYA_NATIVE = false`, `SUPPORTS_SWAPKIT = true`, `ENABLE_ZERO_FEES` (testnet-only constant) | `W/Constants.java:61-146,309` | iOS gates DashConnect to test networks too (IOS-085). |
| Wallets | **One wallet per install.** No multi-wallet and no wallet picker. | `W/WalletApplication.java` | iOS has multi-wallet (IOS-110). |
| Balances | Core (dashj SPV) only, plus the DashPay identity **credit balance** (Tools → Credits). There is **no Shielded/Orchard pool, no Platform (DIP-17) addresses, no advanced mode and no internal transfer.** | — | iOS IOS-019/021/045/053/059–064 do not exist on Android. |
| Tabs | `Home │ Contacts │ Payments │ Explore │ More`. **Contacts and Explore are hidden until the identity has a username.** Without one, Explore is reached from More. Payments is a real tab: a segmented Receive / Pay screen. | `WR/menu/bottom_navigation_menu.xml`, `W/ui/main/MainActivityExt.kt` (`setupBottomNavigation`) | Same tab gating as iOS. On iOS, Payments is a sheet with Send / Receive / Transfer (IOS-041). |
| Engine | dashj (bitcoinj fork) SPV with headers-first, masternode-list-first sync. Platform through `dashj-platform` (`org.dashj.platform.*`). WorkManager jobs for Platform writes. | `W/service/BlockchainServiceImpl.kt`, `W/service/platform/*`, `W/ui/dashpay/work/*` | iOS uses SwiftDashSDK. Desktop uses rs-platform-wallet. |
| Persistence | Encrypted dashj wallet protobuf. PIN and wallet password are wrapped by `SecurityGuard` (Android Keystore, plus a mnemonic-derived fallback key so the PIN can be recovered). Room DB (contacts, profiles, invitations, username requests, votes, imported MN keys, tx metadata, top-ups, display cache). DataStore configs (`WalletUIConfig`, `DashPayConfig`, `ExploreConfig`, `CoinbaseConfig`…). | `W/security/*`, `W/database/{dao,entity}/*`, `W/ui/dashpay/utils/DashPayConfig.kt` | — |
| Theme | Light only. `Theme.AppCompat.DayNight` is declared, but the night colours are commented out. | `common/src/main/res/values/styles.xml:4` | iOS has light and dark (IOS-119). |
| Localisation | 50 `values-*` locales, managed through Transifex scripts in `translations/` | `wallet/res/values-*` | iOS has 43 locales (IOS-118). |
| Analytics | Firebase Analytics, Crashlytics, FCM, Firebase Storage (Explore DB) | `C/services/analytics/*` | iOS uses Firebase too. |

## 23. Flow differences worth carrying into the desktop design

1. **Create wallet.** Android goes 12/24 → PIN → live wallet, and backup is deferred (Secure now / reminder). iOS verifies the phrase first. Desktop already follows iOS (verify first). Keep the Android "Secure now" shortcut as a fallback when a user skips (if skipping is allowed).
2. **Restore.** Android accepts only 12 or 24 words in one wordlist and offers a creation date. iOS accepts 12–24 words in 10 languages with phrase repair. Desktop should take the iOS superset and add Android's date picker as a friendlier birth height.
3. **Payments.** On Android, Payments is a tab (Receive / Pay). On iOS it is a sheet with Send / Receive / Transfer. The desktop sidebar can host it as a page.
4. **Pay to contact auto-accepts** a pending incoming request (Android). Check that iOS and desktop do the same, or document the difference.
5. **Contested usernames.** Android adds a verify-identity link step and an instant secondary name, and More shows request status (requesting / voting / blocked / lost / approved). iOS has a request-status screen and an optional temporary name.
6. **Invite funding.** The invite's type (contested 0.25 or non-contested 0.03) limits which names the invitee may request (invite-specific copy in AND-072). Claim auto-sends a contact request to the inviter on both platforms.
7. **Credits.** Android shows low / empty credit warnings with "Buy Credits" before contact requests and profile updates, and has a real top-up flow. iOS "Buy credits" is a mock (IOS doc §1.22) but has top-up from the profile sheet.
8. **CrowdNode.** Both are wound down. Android shows Staking only for existing accounts and hides deposits. iOS hides sign-up and deposits with a notice. Desktop: withdraw-only for existing accounts, or omit.
9. **Buy & Sell.** Same services (Topper, Uphold, Coinbase, Dash DEX via SwapKit). Android lets the DEX sell flow paste a linked exchange's deposit address (Coinbase / Uphold address sources). No geo gating on Android.
10. **DashSpend.** Same two providers. Android splits purchase into V1 (CTX, BIP70) and V2 (PiggyCards, multi-quantity). It has an order-details view for multi-card orders.
11. **History filter.** Android is single-select (All / Sent / Received / Gift cards). iOS is multi-select with more categories.
12. **Network.** Android uses separate apps per network. The desktop can switch at runtime (like iOS) but must keep testnet-only features gated: DashConnect, faucet, sandbox hosts.
